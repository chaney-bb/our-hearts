## 一、结论：微信小程序 + 云开发

| 项 | 选择 |
|---|---|
| 形态 | 微信小程序（不是 PWA、不是原生 App） |
| 后端 | 微信云开发（自带数据库 + 云函数 + 免运维） |
| 前端 | 小程序原生（WXML / WXSS / JS），不引框架 |
| 插件库 | 不用，UI 手写，样式全在 `app.wxss` 和页面 `wxss` 里 |
| 部署 | 云开发部署；两个人用走「体验版」，不备案不审核 |

### 为什么是它

1. **零运维**。云开发不用买服务器、不用配 HTTPS、不用域名备案，数据库直接在微信后台点着建。这省掉了小白最容易死的那一关。
2. **你对象不用装任何东西**。微信里扫个码就是，比"扫码下载 App / 加到主屏幕"简单一个量级。
3. **Windows 也能完整开发**。原生 App 的 iOS 版本必须有 Mac + Xcode，你连第一个包都打不出来。
4. **改完保存就生效**，不用打包、不用等审核。这条直接决定你俩能不能坚持迭代。
5. **以后能长大**。订阅消息提醒、分享给朋友、正式上架，都是在这个项目上继续加，不用推倒重来。

### 为什么不是另外两条路

- **PWA（网页 App）**：开发也快，但国内要一个能公网访问的 HTTPS 地址（服务器 / 域名备案），且微信里打开体验割裂，对象大概率"用两天就忘了"。
- **原生 App（Flutter / RN）**：最像真 App，但要装 Android Studio、要 iOS 签名、每次改动都要重新打包安装。**这不是你现在该付的成本**。

## 二、第一版做什么（只做一件事，但做完整）

**核心闭环：每晚打卡 → 得爱心 → 爱心换礼物。**

### 2.1 页面（一共 5 个，够了）

| 页面 | 状态 | 内容 |
|---|---|---|
| 首页 / 今日 | ✅ 已有 | 爱心余额、连续天数、两个打卡按钮、配对状态、最近 7 天 |
| 记录 | ✅ 已有 | 月历（早睡/早起/全勤标记）、本月全勤数、最长连续、爱心明细 |
| 商城 | ⬜ M3 | 礼物列表 + 兑换 |
| 兑换记录 | ⬜ M3 | 待兑现 / 已兑现的券 |
| 设置 | ⬜ 以后 | 改昵称、改打卡窗口、解绑 |

### 2.2 打卡规则（默认值，全在 `rules.js` 一个文件里）

| 项目 | 默认规则 |
|---|---|
| 早睡打卡窗口 | 21:30 – 23:59 |
| 早起打卡窗口 | 05:30 – 08:00 |
| 单项打卡 | +1 爱心 |
| 当天两项都完成（全勤） | 额外 +1 |
| 两人同一天都完成同一项（同步奖） | 每人额外 +1 |
| 连续 7 天全勤 | +10 |
| 连续 30 天全勤 | +50 |
| 补签卡 | 商城 10 爱心一张（M3 上线，每月限 2 张） |

**关键设计：判定用服务器时间。**
手机时间可以随手改，把系统时间调到 22:00 就白拿爱心了。所以真正的判定放在云函数里，客户端只负责显示倒计时和按钮状态。

### 2.3 商城规则（M3 再做，但设计先定）

- 礼物由**你俩自己上架**：名字、emoji、价格、兑现说明（"对方洗碗一次"）
- 爱心是**两人共享的一个池子**：比各算各的更甜，也避免"谁买谁亏"的计较
- 兑换后生成一张**券**，状态：待兑现 → 已兑现（由对方点确认）
- **不做充值、不做真钱支付。** 一旦涉及花钱买爱心，就是虚拟货币 + 支付合规问题，个人搞不定，也会毁掉"靠坚持获得"的意义

### 2.4 明确这一版**不做**什么

聊天、相册、纪念日、心情日记、礼物配送、AI 陪伴——全部砍掉。
理由很简单：**功能越多，你俩越不会天天用。** 先把"每天点一下"这个动作固化下来。

## 三、数据怎么存（4 个集合）

```
profiles       openid, nickname, avatarEmoji, coupleId, createdAt
couples        inviteCode, members[openid...], hearts, createdAt
checkins       openid, coupleId, date('2026-10-26'), type(sleep|wake),
               at(时间戳), source(normal|makeup)
heart_logs     openid, coupleId, date, at, delta, reason
```

几个刻意的设计：

- **爱心用流水账（heart_logs），不只有余额。** `couples.hearts` 是方便显示的缓存，真正的账在流水里。出错了能查、能补、能重算——这正是你已有的后端知识最该用上的地方。
- **日期存成字符串 `YYYY-MM-DD`（北京时间）**，不用时间戳。范围查询直接按字符串比大小，跨月统计不用写时区转换。
- **所有表都带 `coupleId`**。以后要支持多对情侣、或者加"我们的小群"，都不用改表结构。
- **打卡判定在云函数**，集合权限设成「所有用户不可读写」，客户端连库都摸不到。

- 项目能编译、页面能显示、手机能扫码看到
- 验收：开发者工具里看到首页，不再是白屏

### ✅ M1 · 单人打卡闭环（1–2 天）
- 打卡按钮 + 时间窗口判定 + 爱心流水 + 连续天数 + 记录日历
- 双模式：没配云开发时走本地预览，配了就上云
- 验收：跑到 `node scripts/smoke-test.mjs` 全绿

### 🟡 M2 · 双人真数据（差真机联调）
- 代码已写：`joinCouple`（邀请码配对）、同步奖、共享爱心池
- 还差：你注册 AppID、开通云开发、建集合、部署云函数，然后两台手机实测
- 验收：两台手机各自打卡，都能看到对方状态，同步奖 +1

### ⬜ M3 · 商城 + 兑换（1–2 天）
- 礼物增删、兑换、券的兑现确认
- 验收：爱心够才能兑换，兑换后余额正确减少，券能核销

### ⬜ M4 · 让它变成习惯（持续）
- 订阅消息：每晚 21:30 提醒"该打卡啦"
- 月度报告：这个月你俩一共攒了多少爱心
- 之后随便加：纪念日倒计时、心情、照片墙

## 五、关于"上线"这件事（别被吓到）

| 用法 | 需要什么 | 要多久 |
|---|---|---|
| 自己在开发者工具里玩 | 无 | 现在 |
| 你和 TA 两个人用（体验版） | 注册小程序个人账号（免费） | 半小时 |
| 给朋友也用（体验版加人，上限 15 人左右） | 把朋友加成体验成员 | 几分钟 |
| 真正上架所有人可用 | 小程序备案 + 提交审核 | 1–3 周 |

**先只用体验版。** 你俩用得爽，比"上架成功"重要一百倍。

## 六、你每天到底怎么"vibe coding"

三步循环，一轮 20–60 分钟：

1. **说清楚要什么**（需求卡片，直接抄改）
   ```
   现在：商城页面还不存在，爱心只能攒着
   我要：加一个商城页，列出礼物（名字/emoji/价格），爱心够就能点兑换，
        兑换后爱心扣掉、生成一张待兑现的券
   不要改：打卡和记录页的逻辑
   做完告诉我：改了哪几个文件、我怎么自己点一遍验证
   ```
2. **自己跑一遍**：AI 说"完成了"不算完成，你亲手点过才算。
3. **提交 git**：`git add -A; git commit -m "加了商城页"` ← 这是你唯一的后悔药。

### 三条铁律

- **一次只改一件事。** 要求越多，AI 越容易把别的功能改坏。
- **先跑通，再好看。** 按钮丑但能打卡 > 漂亮但点不动。
- **报错就贴原文**，不要说"不行了"，要说"报了这个错 + 我点了哪一步"。
- 改完规则一定跑 `node scripts/sync-rules.mjs` 和 `node scripts/smoke-test.mjs`。

## 八、三个最可能踩的坑

1. **想一次做完整套（聊天+相册+商城+打卡）。** 结果每个都是半成品，一个都不能用。
2. **花两周纠结配色、名字、图标。** 这些都能在第 4 天改，别让它们挡住第一次打卡。
3. **做充值 / 付费礼物。** 合规风险 + 破坏"靠坚持获得"的设计初衷，坚决不做。
