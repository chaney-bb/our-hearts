## 一、先补小程序基础（第一次开发必读）

### 1.1 一个页面 = 四个文件

| 文件 | 作用 | 本项目例子 |
|---|---|---|
| `index.js` | 逻辑：数据、生命周期、事件处理 | `pages/m/checkin/index.js` |
| `index.wxml` | 模板：结构，类似 HTML | `pages/m/checkin/index.wxml` |
| `index.wxss` | 样式：类似 CSS，单位多用 `rpx` | `pages/m/checkin/index.wxss` |
| `index.json` | 页面配置：标题、组件、下拉刷新 | `pages/m/checkin/index.json` |

全局还有三个文件：

| 文件 | 作用 |
|---|---|
| `app.js` | 小程序启动入口，只执行一次 |
| `app.json` | 页面路径、tabBar、窗口样式 |
| `app.wxss` | 全局样式（颜色、按钮、卡片） |

> 小程序**没有** DOM、没有 `document`、没有 `window`。你不能用 jQuery，也不能直接操作节点；一切通过 `setData` 改数据，框架负责渲染。

### 1.2 启动与页面生命周期

```js
// app.js（节选）
App({
  globalData: { navTop: 24, mode: 'mock' },
  onLaunch() {
    this.measureNav()
    this.globalData.mode = api.init()   // 决定走云还是本地
  }
})
```

```js
// 页面
Page({
  data: { ready: false },   // 初始数据，模板里用 {{ready}} 读
  onLoad(options) {},       // 页面创建，只一次；能拿路由参数
  onShow() {},              // 每次显示（从别的页面返回也会触发）
  onHide() {},              // 隐藏
  onUnload() {},            // 销毁
  onPullDownRefresh() {}    // 下拉刷新（需要在 json 里开启）
})
```

本项目的习惯：

- **数据加载放 `onShow`**（不是 `onLoad`）：从规则页返回、从审批页返回时能自动刷新。
- **定时器在 `onHide` / `onUnload` 清掉**：打卡页每秒刷新倒计时，离开必须 `clearInterval`。
- **`onLoad` 只做一次性初始化**：比如读 `options.mode`、算 `navTop`。

### 1.3 数据绑定与事件

```xml
<!-- 条件渲染 -->
<view wx:if="{{error}}">{{error}}</view>

<!-- 列表渲染：一定要 wx:key -->
<view wx:for="{{items}}" wx:key="key" data-type="{{item.key}}" bindtap="onCheckin">
  {{item.emoji}} {{item.label}}
</view>

<!-- 三元表达式、逻辑判断都可以写在 {{}} 里 -->
<view class="btn {{item.done ? 'is-done' : ''}}">
  {{item.done ? '已完成' : '打卡'}}
</view>
```

```js
// 事件处理：dataset 拿 data-* 的值
onCheckin(e) {
  const type = e.currentTarget.dataset.type
  this.setData({ busy: true })   // 改数据 → 自动重新渲染
}
```

**三个新手必踩的坑**：

1. `this.setData` 是异步的。刚 `setData` 完立刻读 `this.data.xxx`，可能还是旧值。
2. 事件处理函数里的 `this` 默认指向页面实例，但如果你把函数拆出去、或者用 `function` 回调，`this` 会丢。本项目用 `var self = this` 解决。
3. `wx:for` 不写 `wx:key` 会有性能问题，列表更新时可能错位。

### 1.4 页面跳转

| API | 场景 | 本项目例子 |
|---|---|---|
| `wx.navigateTo` | 打开新页面，可返回 | 首页 → 打卡页、我的 → 审批 |
| `wx.redirectTo` | 替换当前页，不能返回 | 规则只读 → 规则编辑 |
| `wx.switchTab` | 切 tab，必须对应 tabBar 页面 | 登记完成后回首页 |
| `wx.navigateBack` | 返回上一页 | 规则页提交后 |

> tabBar 页面只能用 `switchTab`；`navigateTo` 跳 tabBar 会失败。本项目的 tab 只有「首页 / 我的」。

### 1.5 云开发调用

```js
// miniprogram/core/cloud.js
wx.cloud.callFunction({
  name: 'api',                                  // 云函数名
  data: { action: 'checkin.act', payload: { type: 'sleep' } }
}).then(res => {
  const result = res.result                     // 云函数 return 的东西
})
```

必须先 `wx.cloud.init({ env: '环境ID' })`，否则 `wx.cloud` 是 undefined。
本项目把这件事收在 `core/api.js` 的 `init()` 里，页面永远不直接碰 `wx.cloud`。

### 1.6 异步：Promise 与 async/await

云函数调用、数据库操作都是异步的，返回 Promise。项目里两种写法都有：

```js
// 前端：Promise + then（为了兼容老基础库，没用 async/await）
checkinApi.act(type).then(function (res) {
  if (!res.ok) { ... }
})

// 云函数：async/await（Node.js 环境支持）
async function act(ctx, payload) {
  const records = await store.getRecords(ctx, dayKey)
}
```

**顺序很重要**：`await` 写漏了，后面拿到的就是 Promise 对象，表现为「莫名 undefined」。

### 1.7 样式：rpx 与自定义导航

- `rpx`：屏幕宽度固定为 750rpx。设计稿 375px 时，1px = 2rpx。本项目大量用 `rpx`。
- 本项目 `app.json` 设置了 `"navigationStyle": "custom"`，所以没有系统导航栏；页面自己留出状态栏高度。
- `app.js` 的 `measureNav()` 用 `statusBarHeight + 12` 算出 `navTop`，页面用 `style="padding-top:{{navTop}}px"`。
- 颜色集中在 `app.wxss`：主色 `#FF6B81`，背景 `#FFF7F3`，成功色 `#2FAE8B`。

### 1.8 本地存储

```js
wx.setStorageSync('key', obj)
const obj = wx.getStorageSync('key')
```

本地预览模式（`core/mock.js`）就把全部数据存在 `wx.storage` 的一个 key 里：`our-hearts-mock-v4`。
它只在这台手机上，**不会同步**，所以不能真的和对象配对。

### 1.9 常见报错对照

| 现象 | 原因 | 解决 |
|---|---|---|
| 页面白屏，控制台 `wx.cloud is not defined` | 基础库太低 / 没初始化 | 调高调试基础库；检查 `envId` |
| `FunctionName ... not found` | 云函数没部署 | 右键 `cloudfunctions/api` → 上传并部署 |
| `collection not exist` | 集合没建 | 云开发控制台建集合，权限「所有用户不可读写」 |
| `permission denied` | 集合权限不对 | 改成「所有用户不可读写」 |
| 改了云函数但没生效 | 只上传了小程序，没部署云函数 | 先部署云函数，再编译小程序 |
| 真机白屏、开发者工具正常 | 域名/基础库/隐私接口限制 | 看真机调试日志；检查「详情 → 本地设置」 |

`core/api.js` 的 `explain()` 会把上面这些原始错误翻译成人话，首页会直接显示。

## 三、启动链路：从点开小程序到看见首页

### 3.1 启动顺序

```
微信启动小程序
  → app.js onLaunch()
      → measureNav()           算出状态栏下方留白
      → api.init()             读 utils/config.js 的 envId
          ├─ envId 为空        → mode = 'mock'，用 core/mock.js
          ├─ 没有 wx.cloud     → mode = 'mock'，记录 lastError
          ├─ wx.cloud.init 抛错 → mode = 'mock'
          └─ 成功              → mode = 'cloud'，用 core/cloud.js
  → app.json 的第一个页面 pages/home/home
      → home onLoad()  取 navTop / mode
      → home onShow()  → load()
          → session.get()
          → 渲染宫格
          → 对每个 enabled 模块并行调 <key>.summary
```

### 3.2 `api.init()` 的决策

```js
// miniprogram/core/api.js:17
function init() {
  var envId = String(config.envId || '').trim()
  if (!envId) { mode = 'mock'; client = mock; return mode }
  if (!wx.cloud) { /* 基础库太低 */ mode = 'mock'; client = mock; return mode }
  try {
    wx.cloud.init({ env: envId, traceUser: true })
    mode = 'cloud'; client = cloud
  } catch (err) {
    lastError = 'wx.cloud.init 失败：' + ...
    mode = 'mock'; client = mock
  }
  diagnose(envId)
  return mode
}
```

**设计意图**：云开发出任何问题，界面都不能白屏。
最坏情况自动降级到本地预览，用户至少能看到界面；首页还会给「先用本地模式」按钮。

### 3.3 首页 `load()` 做了什么

```js
// miniprogram/pages/home/home.js:46
load: function () {
  return session.get().then(function (s) {
    if (!s || !s.ok) { self.fail(s); return }

    // ① 没登记 → 只显示登记引导卡
    if (s.needRegister) { self.setData({ needRegister: true }); return }

    // ② 先铺宫格（数据来自 core/modules.js）
    var grid = registry.slice().sort(byOrder).map(toCard)

    // ③ 渲染会话：我 / 对方 / 两个钱包 / 在一起天数 / 邀请码
    self.setData({ ready: true, me: s.me, partner: s.partner, hearts: ..., grid: grid })

    // ④ 没配对就不问模块（门禁会拒）
    if (!s.bound) return

    // ⑤ 每个已上线模块并行要一句 summary，填到宫格卡片上
    return Promise.all(mods.filter(enabled).map(m => api.call(m.key + '.summary')))
      .then(arr => self.setData({ grid: withSub }))
  })
}
```

**为什么首页不认识「打卡」**：它只认 `registry` 数组和 `<key>.summary` 协议。
加模块时首页一行不用改，`core/modules.js` 加一条即可。

## 四、小程序端逐文件讲解

### 4.1 `core/api.js` —— 唯一数据入口

对外 4 个方法：

| 方法 | 作用 |
|---|---|
| `init()` | 决定 `cloud` / `mock`，返回模式字符串 |
| `call(action, data)` | 统一调用；失败时把原始错误翻译成人话，返回 `{ok:false,...}` |
| `forceLocal(reason)` | 运行中强制切本地（首页「先用本地模式」按钮） |
| `getMode()` / `getLastError()` | 给页面显示当前模式 / 诊断信息 |

`call()` 的关键是**永远不把裸错误抛给页面**：

```js
function call(action, data) {
  return client.call(action, data || {}).catch(function (err) {
    var raw = (err && (err.raw || err.errMsg || err.message)) || '未知错误'
    lastError = explain(raw)
    return { ok: false, code: 'CLOUD_ERROR', message: lastError, raw: raw }
  })
}
```

这样页面只需要判断 `res.ok`，不用写 try/catch。

### 4.2 `core/cloud.js` —— 23 行的薄封装

只做一件事：把 `{action, payload}` 发给云函数 `api`，把 `res.result` 返回；失败时保留 `raw` 和 `errCode`。
**不在这里做重试**：打卡的防重放在服务端（幂等 + 唯一记录），客户端重试反而危险。

### 4.3 `core/mock.js` —— 本地预览模式

- 数据全部在 `wx.storage` 的 `our-hearts-mock-v4`。
- 内置一个假对象「亲爱的」和 86 爱心，所以一打开就有内容。
- 支持：`session.get/register/bind/unbind/ledger`、`checkin.summary/detail/act/history`、`approvals.list`。
- 不支持：真实配对、真实审批（`checkin.appeal` / `proposeConfig` / `approvals.decide` 返回「本地预览不能审批」）。
- 规则同样走 `normalizeConfig(s.settings)`，所以离线也能看规则变更效果。

**它和云端的行为差异**：

| 行为 | 云端 | 本地预览 |
|---|---|---|
| 数据共享 | 两台手机同步 | 只在这台手机 |
| 配对 | 真邀请码 | 输入任意 6 位就成功 |
| 审批 | 有工单 | 直接提示不支持 |
| 扣分结算 | 定时 + 惰性 | 不扣分（没有 settle） |
| 月度全勤 | 幂等键防重复 | `monthlyAwarded` 标记防重复 |

### 4.4 `core/session.js` —— 会话门面

页面不直接拼 `session.xxx` 字符串，而是调这里的方法：

| 方法 | 对应 action |
|---|---|
| `get()` | `session.get` |
| `register(data)` | `session.register` |
| `updateProfile(data)` | `session.updateProfile` |
| `bind(inviteCode)` | `session.bind` |
| `unbind()` | `session.unbind`（固定传 `confirm: true`） |
| `verify()` | `session.verify` |
| `ledger()` | `session.ledger` |
| `listApprovals()` | `approvals.list` |
| `decideApproval(id, approve)` | `approvals.decide` |

### 4.5 `pages/home` —— 外壳

界面结构（`home.wxml`）：

```
┌ 顶部 hero（粉色渐变）
│  在一起第 N 天          两个头像
│  ❤️ 86 我的爱心
│  🐻 小肚肚 💗 102
├ 未配对：邀请码卡片 + 输入 TA 的邀请码
├ 我们的小功能（两列宫格，来自 core/modules.js）
│  [早睡早起]  [消费申请·待上线]
│  [吃饭点餐·待上线] [下一个功能]
└ 本地模式提示（仅 mock 时）
```

三种状态：`needRegister`（登记引导）、`error`（云连接失败 + 重试/切本地）、`ready`（正常）。

### 4.6 `pages/mine` —— 我的

- `session.get()` 显示资料、对方、在一起天数、邀请码。
- 已配对时额外调 `approvals.list`，把 `toMe.length` 显示成「消息申请」右边的红色数字徽标。
- 操作入口：消息申请、修改资料、爱心明细、解除绑定。
- **解绑要弹两次确认**（`mine.js:82`），第二次才调 `session.unbind()`；服务端还要求 `confirm === true`，双保险。

### 4.7 `pages/register` —— 登记 / 修改资料

- 6 项必填：userId、真实姓名、手机号、生日、性别；自我介绍选填。
- 头像从 10 个 emoji 里选。
- `mode=edit` 时先 `session.get()` 回填，提交走 `updateProfile`；否则走 `register`。
- 前端只做「非空」校验；格式校验（手机号、userId 字符集、长度）全在服务端 `identity.normalizeProfile`。
- 生日用 `<picker mode="date">`，所以格式天然是 `YYYY-MM-DD`。

### 4.8 `pages/approvals` —— 工单列表

- 两个列表：`toMe`（待我处理，只有 pending）和 `mine`（我发起的，含历史状态）。
- 状态文案：`pending 等对方处理 / approved 已同意 / rejected 已拒绝 / expired 已过期`。
- 点同意/拒绝 → 二次确认 → `decideApproval(id, approve)` → 刷新列表。
- 服务端会再校验「这张工单是不是给你的」「是不是已经处理过」。

### 4.9 `pages/ledger` —— 爱心流水

- 调 `session.ledger`，显示余额 + 最近 50 条流水。
- 每条：原因、`+2/-1`、日期、时间。
- 如果 `heart_logs` 集合不存在，服务端返回 `warn`，页面显示提示而不是整页报错。

### 4.10 `pages/m/checkin` —— 打卡页

这是模块的主页面，第九节会逐段拆。先记住它只做四件事：

1. 拉 `checkin.detail()`，拿到今日状态、当月日历、漏卡、规则。
2. 每秒用「服务器偏移」重算倒计时和按钮可用状态。
3. 点打卡 → `checkin.act(type)` → 飘一个 `+N ❤️` → 重新拉详情。
4. 漏卡卡片 → `checkin.appeal()` 提交申诉；右上角 ⋯ → 规则只读/编辑。

### 4.11 `pages/m/checkin/rules` —— 规则页

- `mode=view`：把规则翻译成几句人话（`buildSummary`）。
- `mode=edit`：时间选择器 + 数字输入，改完先本地 `validateConfig`，再 `checkin.proposeConfig` 提交工单。
- 编辑时的联动：改窗口开始/结束，会自动把第一档/最后一档的边界对齐；改某一档结束，下一档开始跟着走。
- 提交成功 ≠ 生效：要对方在「消息申请」里同意，才写入 `core_settings`。

## 五、云函数入口与路由

### 5.1 `index.js` 主流程

```js
exports.main = async (event) => {
  const action = String(event.action || '')
  const payload = event.payload || {}

  // ① 身份：云函数从微信上下文拿 openid，客户端伪造不了
  let openid = ''
  try { openid = cloud.getWXContext().OPENID } catch (e) {}
  if (!openid) return respond.fail('NO_OPENID', '拿不到用户身份，请从微信里打开')

  // ② 旧接口名：给友好提示，而不是「没有这个功能」
  if (LEGACY[action]) return respond.fail('CLIENT_OUTDATED', '界面还是旧版本，点一下「编译」')

  try {
    // ③ 定时结算：只允许定时触发器或测试强制触发
    if (action === 'settle.run') {
      const isTimer = event.Type === 'Timer' || event.type === 'timer' || payload.force === true
      if (!isTimer) return respond.fail('FORBIDDEN', '结算只能由定时触发器调用')
      return respond.ok(await scheduler.runAll(Date.now()))
    }

    // ④ 系统动作：session.* / approvals.*
    if (SYSTEM[action]) return respond.ok(await runSystem(action, payload, openid))

    // ⑤ 模块动作：'checkin.act' → registry.get('checkin').actions.act
    const seg = action.split('.')
    if (seg.length !== 2) return respond.fail('BAD_ACTION', '接口名不对：' + action)
    const mod = registry.get(seg[0])
    if (!mod) return respond.fail('NO_MODULE', '没有这个功能：' + seg[0])
    const fn = mod.actions[seg[1]]
    if (!fn) return respond.fail('NO_ACTION', '没有这个动作：' + seg[1])

    // ⑥ 组装 ctx（含两道门禁），执行模块动作
    const ctx = await context.create(mod, openid)
    const result = await fn(ctx, payload)
    if (result && result.ok === false) return respond.fail(result.code, result.message)
    return respond.ok(result)
  } catch (err) {
    // ⑦ 业务错误 vs 系统错误分开
    if (err && err.biz) return respond.fail(err.code, err.message)
    console.error('[api 出错]', action, err)
    return respond.fail('ERROR', '云函数执行出错（' + action + '）', detail)
  }
}
```

### 5.2 系统动作表

| action | 做什么 | 是否受配对门禁 |
|---|---|---|
| `session.get` | 我是谁 / 对方 / 两个钱包 / 在一起天数 / 邀请码 | 否（没配对也要能看） |
| `session.register` | 首次登记 6 项 | 否 |
| `session.updateProfile` | 改资料（userId 重新查重） | 否 |
| `session.bind` | 输入邀请码配对 | 否（本身就是在配对） |
| `session.unbind` | 解绑 + 双方清零 + 新建 pending 关系 | 需已配对（内部判断） |
| `session.verify` | 钱包余额 vs 流水之和 | 否 |
| `session.ledger` | 最近 365 天流水（取前 50 条） | 否 |
| `approvals.list` | 待我处理 + 我发起的 | 否 |
| `approvals.decide` | 同意/拒绝 | 需已配对 |

### 5.3 返回信封

成功：

```json
{ "ok": true, "serverNow": 1730000000000, "...": "模块返回的字段" }
```

失败：

```json
{ "ok": false, "code": "NOT_YET", "message": "早睡打卡 21:30 开放（云端现在 21:12）", "serverNow": ... }
```

系统异常才带 `detail`（原始错误），业务失败**不允许吞原因**。

### 5.4 为什么 `settle.run` 要校验调用方

如果不校验，任何客户端都能调 `settle.run` 强制结算。虽然结算本身是幂等的，但会：
- 绕过定时器频率，增加日志噪音；
- 在规则刚改、数据没准备好时提前扣分。

所以只认 `event.Type === 'Timer'`，或测试时 `payload.force === true`。

### 6.2 `core/errors.js` + `core/respond.js`

```js
function bizError(code, message) {
  const err = new Error(message || code)
  err.biz = true       // 标记：这是业务失败，不是系统异常
  err.code = code
  return err
}
```

```js
function ok(data)   { return Object.assign({ ok: true, serverNow: Date.now() }, data) }
function fail(code, message, detail) { ... }
function biz(code, message, extra)  { ... }   // 模块里直接 return 的业务失败
```

**两种业务失败**：

| 方式 | 场景 | 路由层怎么处理 |
|---|---|---|
| `throw bizError(...)` | 内核/门禁（没登记、没配对、余额不够） | catch 后转成 `{ok:false, code, message}` |
| `return respond.biz(...)` | 模块动作里的可预期失败（还没到时间、今天打过了） | 路由层看到 `ok === false` 原样返回 |

### 6.3 `core/clock.js` —— 时间服务

云函数运行环境是 **UTC**，所以所有「北京时间」都要手动加 8 小时。

| 函数 | 作用 | 例子 |
|---|---|---|
| `parts(ms)` | 拆成北京时间年月日时分 | `{y:2026,m:10,d:27,h:22,mi:14,dow:2}` |
| `dateKey(ms)` | `YYYY-MM-DD` | `'2026-10-27'` |
| `timeKey(ms)` | `HH:mm` | `'22:14'` |
| `monthKey(ms)` | `YYYY-MM` | `'2026-10'` |
| `minutesOf('21:30')` | 一天中的分钟数 | `1290` |
| `dayMinutes(ms)` | 当前时刻的分钟数 | `1334` |
| `shiftKey(key, n)` | 日期 key 加减天 | `'2026-10-31' + 1 → '2026-11-01'` |
| `wallToEpoch(y,m,d,h,mi)` | 北京时间 → 时间戳 | 用于算窗口关闭时刻 |
| `msUntilTime('23:59', ms)` | 距今天某钟点还有多久 | 可为负 |
| `humanize(ms)` | 毫秒说人话 | `'7 小时 46 分'` |

**注意**：`shiftKey` 用的是 `Date.UTC`，不涉及时区；`wallToEpoch` 会减 8 小时。两者不要混用错。

### 6.4 `core/identity.js` —— 身份与关系

#### 校验（`normalizeProfile`）

| 字段 | 规则 | 错误码 |
|---|---|---|
| `userId` | 2~12 字，中文/字母/数字/下划线/短横线，全局唯一 | `BAD_USER_ID` / `USER_ID_TAKEN` |
| `realName` | 2~20 字 | `BAD_REAL_NAME` |
| `phone` | `^1\d{10}$`（只手填） | `BAD_PHONE` |
| `birthday` | `YYYY-MM-DD` | `BAD_BIRTHDAY` |
| `gender` | `male/female/other` | `BAD_GENDER` |
| `bio` | ≤100 字 | `TOO_LONG` |
| `avatarEmoji` | ≤8 字，默认 🙂 | — |

> 手机号只能手填：个人主体小程序用不了「手机号快速验证」组件（需要主体认证）。
> 真实姓名没有自动核验。这两项属于要声明收集的个人信息，上线前必须配《用户隐私保护指引》。

#### 关系的三个状态

```
pending    已登记 / 还没配对
active     已配对，可以使用功能
dissolved  已解绑，数据封存（旧数据永远留在这个 coupleId 下）
```

老数据没有 `status` 字段时，`statusOf()` 按成员数推断：`members.length >= 2` 就是 `active`。

#### 首次打开会自动建档

`getProfile(openid)` 查不到时，会：
1. 建一条 `profiles`（只有 openid，`userId` 为空 → 表示「还没登记」）；
2. 建一条 `couples`（`status: 'pending'`，`members: [openid]`，生成 6 位邀请码）。

所以「未登记」不是没有档案，而是 `profile.userId` 为空。
门禁判断的也是这个字段。

#### 配对 `joinCouple(openid, code)`

```
1. 必须已登记（userId 非空）
2. 按 inviteCode 找对方的关系；找不到 → NOT_FOUND
3. 不能是自己的邀请码 → SELF
4. 对方关系必须是 pending 且只有 1 人 → 否则 FULL
5. 把 openid 加入 members，status = active，写 pairedAt
6. 我的 profile.coupleId 改成对方的关系 id
7. 删掉我自己那条「从没被用过」的 pending 关系（有打卡记录就不删）
```

三条硬约束由此保证：一人只属于一段关系 / 一段关系最多两人 / 配对后双方 `coupleId` 一致。

> 缺口：`joinCouple` 只检查「目标关系是否 pending / 满员」，**没有检查自己是否已经在一段 active 关系里**。
> 界面在已配对时隐藏了输入入口，但直连云函数仍可绕过。修复见 T72。

#### `publicProfile(p)`

只返回双方可见的字段：`userId/displayName/realName/phone/birthday/gender/bio/avatarEmoji`。
**不返回 openid**（openid 只在服务端和 `ctx` 里用）。

### 6.5 `core/settings.js` —— 规则合并

```
模块 defaults（代码兜底）
      +
core_settings 里该 couple + module 的 patch（用户覆盖，完整快照）
      ↓
deepMerge → ctx.config（唯一生效版本）
```

| 函数 | 作用 | 关键点 |
|---|---|---|
| `deepMerge(base, patch)` | 深合并 | **只接受 base 里出现过的键**；数组整体替换（`tiers` 换一整套） |
| `load(coupleId, mod)` | 读当前生效配置 | 集合不存在/没配置 → 返回 defaults，不影响功能 |
| `save(coupleId, module, patch)` | 保存完整快照 | `history[]` 保留最近 20 次，给「按当日生效规则结算」留口子 |
| `configAt(coupleId, mod, ts)` | 某个时间点生效的规则 | 取 `history` 里 `at <= ts` 的最新一版 |

**为什么存完整快照而不是差异**：
- 同意后规则长什么样完全可预期；
- 以后我改默认值，不会悄悄影响你们已配置的规则；
- 结算历史某天时，能精确还原那天用的规则。

### 6.6 `core/hearts.js` —— 爱心账本

第七节单独讲，这里先记住三个入口：

```js
hearts.ensureWallet(openid, coupleId)   // 拿钱包，没有就按流水重算建一个
hearts.apply(ctx, entries, extra)       // 记一笔（或多笔）账
hearts.balanceOf(openid, coupleId)      // 查余额
```

### 6.7 `core/approvals.js` —— 工单状态机

```
pending ──同意──► approved
   │
   ├──拒绝──► rejected
   └──过期──► expired（预留，当前没有自动过期任务）
```

| 函数 | 作用 |
|---|---|
| `create(opts)` | 创建工单；同一 `(module, type, refId, fromOpenid)` 只能有一个 pending |
| `list(openid, coupleId)` | 返回 `{ toMe, mine }`；`toMe` 只含 pending |
| `decide(openid, coupleId, id, approve, registry)` | 校验归属/状态 → 改状态 → 调模块 `onDecision` |

**内核只管状态机，不管业务后果**：
- 打卡模块的 `onDecision.late_night` 负责退分；
- `onDecision.rules_change` 负责写配置；
- 以后的消费申请模块自己实现「同意后记账」。

**一个已知边界**：`decide` 先把工单状态改成 `approved`，再调模块回调。
如果回调抛错，工单已经是「已同意」，但业务没生效，只记录 `applied.error`，**没有自动重试**。
解决办法（以后做）：回调幂等 + 失败补偿任务，或把状态流转和业务写入放进事务。

### 6.8 `core/scheduler.js` —— 定时任务

```js
async function runAll(now) {
  const mods = registry.list().filter(m => typeof m.actions.settle === 'function')
  const couples = await db.collection('couples').limit(200).get()
  const active = couples.data.filter(c => c.members.length >= 2 && (!c.status || c.status === 'active'))

  for (const couple of active)
    for (const openid of couple.members)
      for (const mod of mods) {
        const ctx = await context.create(mod, openid)
        await mod.actions.settle(ctx, {})
      }
}
```

**它只做「把所有人叫一遍」**，不判断扣不扣分。加一个新模块的定时逻辑，只要实现 `actions.settle`，这里一行不用改。

> 两个人用，全量扫没问题。以后人多要改成分页/游标，别在这里加业务。

### 6.9 `core/context.js` —— 组装 `ctx` 与两道门禁

```js
async function create(mod, openid) {
  const profile = await identity.getProfile(openid)

  // 门禁 1：没登记不能玩
  if (!profile.userId) throw bizError('NEED_REGISTER', '先把登记信息填完')

  const couple = await identity.getCouple(profile.coupleId)
  const paired = identity.isPaired(couple)

  // 门禁 2：没配对不能用任何模块（requiresPair:false 可关）
  if (!paired && mod.requiresPair !== false) {
    throw bizError('NOT_PAIRED', '先和 TA 配对才能用这个功能')
  }

  const config = await settings.load(profile.coupleId, mod)

  const ctx = {
    openid, me, coupleId, couple, coupleStatus, partner, isPaired,
    now: Date.now(),                 // 服务器时间
    dateKey: clock.dateKey(now),
    config,
    db: scopedDb(mod),               // 只能碰 mod.collections
    award, penalize, balance, emit
  }
  return ctx
}
```

`scopedDb(mod)` 是「最小权限原则」的代码化：

```js
function scopedDb(mod) {
  const allowed = mod.collections || []
  return {
    collection(name) {
      if (allowed.indexOf(name) < 0) {
        throw new Error('模块 ' + mod.key + ' 无权访问集合 ' + name)
      }
      return db.collection(name)
    }
  }
}
```

模块即使想 `ctx.db.collection('heart_logs')` 也拿不到（没声明）。**这比写十条规范都管用。**

### 6.10 `core/session.js` —— 会话与解绑

`session.get` 返回：

| 字段 | 含义 |
|---|---|
| `needRegister` | `!profile.userId` |
| `needPair` | `!paired` |
| `bound` | 是否已配对 |
| `coupleStatus` | `pending/active/dissolved/none` |
| `me` / `partner` | 公开资料 |
| `inviteCode` | 当前关系的邀请码 |
| `daysTogether` | 从 `pairedAt`（没有则 `createdAt`）算起，+1 |
| `wallet.balance` / `partnerWallet.balance` | 两个钱包 |

`unbind(openid, confirm)` 四步：

```
1. 双方钱包各写一条反向流水：delta = -balance，reason = '解除绑定清零'
2. 把当前关系 status 改成 dissolved，写 dissolvedAt
3. 双方各自新建一条 pending 关系（新邀请码）
4. 双方的 profile.coupleId 指向各自的新关系
```

**为什么用反向流水而不是直接 `balance = 0`**：
直接改 0 会让「余额 = 流水之和」永久破裂，以后查「这人到底赚过多少」就查不出来了。
反向流水既满足「清零」，又保留完整历史。

## 七、爱心加减系统（重点）

### 7.1 为什么必须有一个「账本」

假设 6 个模块都自己发爱心、自己改余额：
- 商城无法统一扣款；
- 余额和记录对不上时，不知道信谁；
- 某个模块写错一次，永远查不出来。

所以内核只留**一个写入口**，模块只能「赚」和「扣自己」，不能直接改余额。

### 7.2 数据模型

```
core_wallets     _id = openid        ← 单用户事务只按 doc(openid) 操作
  openid, coupleId, balance, updatedAt

heart_logs       自动 _id            ← 只追加，永不修改
  openid, coupleId, date, at, delta, reason,
  module, refId, idemKey
```

**余额 = 流水之和**，钱包只是缓存。这不是「多此一举」，而是：
- 出错了能重算；
- 能查每一笔的来源；
- 解绑清零、申诉退分、订单退款都用「反向流水」表达，历史完整。

### 7.3 加爱心：`ctx.award`

```js
// 模块里
await ctx.award(2, '早睡打卡', { refId: dayKey })

// context.js 里
award: async function (n, reason, opts) {
  return hearts.apply(
    ctx,
    [{ delta: n, reason: reason, refId: opts.refId || '', idemKey: opts.idemKey || '' }],
    { now: ctx.now, dateKey: ctx.dateKey, module: mod.key }
  )
}
```

`hearts.apply` 的实际步骤：

```
1. ensureWallet(openid)                  没有钱包就按流水重算建一个
2. 对每一条 entry：
   a. 有 idemKey？查 heart_logs 里是否已有 (openid, idemKey)
      有 → 跳过（本次不重复发）
   b. 写一条 heart_logs（先写流水）
3. total 为 0 → 直接返回 0（不更新钱包）
4. after = wallet.balance + total
   after < 0 → 抛 INSUFFICIENT（爱心不够）
5. 更新 core_wallets：balance = _.inc(total)
6. 返回 total
```

**注意第 2b 和 4 的顺序**：当前实现是「先写流水，再检查余额」。
所有现有调用方都做了保护（`penalize` 先 clamp 到余额，`clearToZero` 正好扣完），所以不会触发。
但以后写商城扣款时，**必须先校验余额再写流水**，否则会出现「流水写了、钱包没扣」的破账。
这是本项目最重要的一个「以后要修」的点（见第十一节风险）。

### 7.4 扣爱心：`ctx.penalize`（扣到 0 封顶）

```js
penalize: async function (n, reason, opts) {
  const balance = await hearts.balanceOf(ctx.openid, ctx.coupleId)
  const amount = Math.min(Math.max(0, n), Math.max(0, balance))
  if (amount <= 0) return 0
  return hearts.apply(ctx, [{ delta: -amount, ... }], ...)
}
```

例子：余额 3，扣 5 → 实际扣 3，返回 3，余额 0。
余额 0，扣 1 → 返回 0，**不写流水**。

> ⚠ 与早期设计文档的差异：原设计写的是「扣到 0 了，记一条『已归零』的流水」。
> 当前代码在余额为 0 时直接返回，没有写这条记录。后果：
> 幂等键没有落库，如果这个人之后在结算窗口内又有了爱心，同一笔漏打可能被再次扣。
> 因为 `settle` 只看最近 3 个打卡日，影响窗口很小，但属于「文档与实现不一致」，已记入待办。

### 7.5 扣到 0 的语义（为什么不做负数）

| 场景 | 结果 |
|---|---|
| 我熬夜没打卡 | 扣我的，扣到 0 为止 |
| 我断更学习计划 | 同上 |
| 对方违反规定 | 只扣对方的，我的不动 |
| 对方余额 0 | 停止扣，不产生负债 |

情侣 App 里「你欠我 30 爱心」会变成吵架素材；兑换逻辑也要处理负数。**扣到 0 为止最省事。**

### 7.6 惰性迁移：老数据怎么变成个人钱包

`ensureWallet(openid, coupleId)`：

```js
const exist = await readWallet(openid)
if (exist) return exist

const balance = await sumLogs(openid)       // 按历史流水重算
await db.collection('core_wallets').doc(openid).set({
  data: { openid, coupleId, balance, updatedAt: Date.now() }
})
return wallet
```

好处：
- 不用跑迁移脚本、不用停机、不用平分；
- 因为每一笔流水本来就记了 `openid`，重算就等于实际所得；
- 老用户第一次被访问时自动建档。

**限制**：`sumLogs` 只取 1000 条（`limit(1000)`）。流水超过 1000 条的用户会被算少。
两个人日常使用几年都到不了，但这是个已知上限。

### 7.7 解绑清零：`clearToZero`

```js
const balance = await balanceOf(openid, coupleId)
if (!balance) return 0
return apply({ openid, coupleId }, [{
  delta: -balance,
  reason: '解除绑定清零',
  idemKey: 'unbind:' + coupleId + ':' + openid
}], ...)
```

余额 0 时不写流水；幂等键避免重复解绑重复清零。

### 7.8 对账：`session.verify`

```js
async function verify(openid, coupleId) {
  const wallet = await ensureWallet(openid, coupleId)
  const sum = await sumLogs(openid)
  return { wallet: wallet.balance, ledger: sum, ok: wallet.balance === sum }
}
```

前端暂时没有入口，但排查问题时可以直接在云函数测试里调。
以后可以放「我的 → 设置 → 高级 → 对账」。

### 7.9 一笔账的完整生命周期（例子）

初始：`balance = 0`，`logs = []`

| # | 事件 | 流水 | 钱包 | 说明 |
|---|---|---|---|---|
| 1 | 21:40 早睡 +2 | `+2 早睡打卡` | 2 | 档位 21:30–22:15 |
| 2 | 06:30 早起 +1 | `+1 早起打卡` | 3 | 档位 06:00–09:00 |
| 3 | 当晚全勤，但月度只有 1 天 | — | 3 | 未到 22 天 |
| 4 | 10-28 00:00 结算 10-27 的早睡 | `-1 早睡漏打 2026-10-27` | 2 | `idemKey=miss:sleep:2026-10-27` |
| 5 | 申诉通过 | `+1 申诉通过退回` | 3 | `idemKey=appeal:<ticket>` |
| 6 | 解绑 | `-3 解除绑定清零` | 0 | 流水总和 = 0，账仍平 |

任何时刻：`balance === sum(delta)`。

### 7.10 并发与失败模式（如实说明）

| 场景 | 会发生什么 | 严重度 | 缓解 |
|---|---|---|---|
| 连点两次打卡 | 客户端 `busy` 锁 + 服务端查 `checkins` 已有记录 + 返回 `DUP` | 低 | 已有 |
| 网络重试同一笔奖励 | `idemKey` 查重后跳过 | 低 | 已有（但非原子） |
| 定时器与用户打开同时结算同一漏打 | 两边都查到没有流水，可能各写一条 `-1` | 低（概率极小） | 幂等键 + 以后加唯一索引/事务 |
| 两个扣款并发 | 都读到旧余额，`after` 都判断通过，`_.inc` 把余额扣成负数 | 中（上商城后才可能出现） | 扣款前原子校验/事务 |
| 写流水成功、更新钱包失败 | 流水多一条，余额没变 | 中 | `verify` 能发现；以后加重试/事务 |
| 工单已通过、模块回调失败 | 状态 approved，业务没生效 | 中 | 记录 `applied.error`；以后补偿 |

> 这些不是「现在就会炸」的 bug，而是架构在「两人使用」规模下的已知取舍。
> 一旦上商城（真扣爱心），必须先处理第 3、4、5 条。

## 八、幂等设计（重点）

### 8.1 什么是幂等，为什么情侣打卡需要它

幂等 = **同一个操作执行一次和执行多次，结果一样**。

这个项目里，下面这些都会导致「同一件事被执行多次」：

- 用户手抖连点两下「打卡」；
- 手机网络抖动，小程序自动重试云函数；
- 定时器每小时跑一次，同一笔漏打被反复扫到；
- 用户从两个页面同时触发结算（首页 `summary` + 打卡页 `detail`）；
- 审批页连点两次「同意」。

如果没有幂等：爱心会重复发、重复扣，账立刻乱。

### 8.2 项目里的四种幂等机制

| # | 机制 | 位置 | 幂等键 / 判据 | 防什么 |
|---|---|---|---|---|
| 1 | 流水幂等键 | `hearts.apply` | `idemKey` + openid | 同一笔奖励/扣分重复写 |
| 2 | 业务唯一记录 | 打卡 `act` | `(openid, coupleId, date, type)` 已存在 → `DUP` | 同一天同一项打两次 |
| 3 | 工单唯一 pending | `approvals.create` | `(module, type, refId, fromOpenid, status=pending)` | 同一件事重复提交申请 |
| 4 | 结算幂等键 | 打卡 `settle` | `miss:<type>:<打卡日>` | 定时器/惰性重复扣分 |

另外还有两个「天然幂等」的设计：
- `core_wallets.doc(openid).set(...)`：不存在就创建，存在就覆盖（惰性迁移不会建出两个钱包）；
- `settings.save` 按 `(coupleId, module)` 查找后 `set`：同一模块只有一份配置。

### 8.3 幂等键命名规范

| 业务 | 键格式 | 代码位置 |
|---|---|---|
| 漏打扣分 | `miss:<type>:<打卡日>` | `modules/checkin/index.js:83` |
| 月度全勤 | `monthly:<YYYY-MM>` | `modules/checkin/index.js:244` |
| 申诉退回 | `appeal:<ticketId>` | `modules/checkin/index.js:421` |
| 解绑清零 | `unbind:<coupleId>:<openid>` | `core/hearts.js:152` |
| 订单支付（规划） | `order:<orderId>:<openid>` | 见 [`../module-dev/shop/规则文档.md`](../module-dev/shop/规则文档.md) |

规范：`<业务>:<业务主键>[:<用户>]`。**不要用时间戳/随机数**，那样每次都不同，等于没幂等。

### 8.4 代码走读：`hearts.apply` 的幂等

```js
for (const e of items) {
  if (e.idemKey) {
    const dup = await db.collection('heart_logs')
      .where({ openid: ctx.openid, idemKey: e.idemKey })
      .count()
    if (dup.total > 0) continue          // ← 已经有这笔，跳过
  }

  total += e.delta
  await db.collection('heart_logs').add({ data: { ..., idemKey: e.idemKey || '' } })
}

if (!total) return 0                     // ← 全是重复，钱包不动
```

**它解决了什么**：顺序重试（第一次成功、第二次再来）不会重复发。
**它没解决什么**：两个请求**同时**查到 0 条，然后都插入 → 两条。这需要数据库唯一索引或事务。

### 8.5 工单的幂等

```js
const dup = await db.collection('core_approvals').where({
  module, type, refId, fromOpenid, status: 'pending'
}).count()
if (dup.total > 0) throw bizError('TICKET_EXISTS', '这件事已经提交过申请了')
```

注意 `refId` 的设计：
- 申诉：`refId = dayKey + ':' + type`（同一天同一项只能申诉一次）；
- 改规则：`refId = 'rules:' + Date.now()`（每次提交都是一张新工单，允许反复改）。

### 8.6 结算的幂等

```js
const amount = await ctx.penalize(t.missPenalty, label + '漏打 ' + day, {
  idemKey: 'miss:' + type + ':' + day,
  refId: day
})
```

`settle` 会被调用很多次：
- 定时器每小时一次；
- 每次打开首页（`summary`）；
- 每次打开打卡页（`detail`）；
- 每次打卡后（`act` 内部又调 `detail`）。

因为 `idemKey` 固定，跑多少次都只扣一次。

### 8.7 幂等的边界

| 情况 | 幂等是否生效 | 说明 |
|---|---|---|
| 顺序重试 | ✅ | 第二次查到已有流水，跳过 |
| 并发重试 | ❌（理论） | 先查后写不是原子操作 |
| 扣分时余额为 0 | ❌ | 不写流水 → 没留下幂等键 → 以后可能补扣 |
| 工单回调失败 | ❌ | 状态已改，业务没做，没有重试 |
| 用户手动改数据库 | ❌ | 任何幂等都防不了 |

### 8.8 怎么把它做「更强」（以后上商城前）

1. **唯一索引**：如果云开发控制台支持唯一索引，给 `heart_logs` 建 `(openid, idemKey)` 唯一索引（`idemKey` 为空的记录要排除，或给空值生成唯一值）。
2. **事务**：云开发数据库支持 `db.startTransaction()` / `runTransaction`（以当前 SDK 文档为准）。把「查重 + 写流水 + 改余额」放进一个事务。
3. **状态机**：订单/工单用「条件更新」推进（只有 `status=pending` 才能改成 `paid`），比先读后写可靠。
4. **扣款前校验**：`hearts.apply` 把「余额是否足够」移到写流水之前；或提供 `hearts.spend` 专用方法。
5. **补偿任务**：记录 `applied.error` 的工单，定时重试或人工处理。

## 九、打卡模块深度讲解（最重点）

> 这是整个项目最完整、也最值得学的模块。看懂它，你就会写第二个模块。

### 9.1 业务一览

| 项 | 规则 |
|---|---|
| 早睡窗口 | 21:30 – 24:00（左闭右开） |
| 早睡档位 | 21:30–22:15 `+2`；22:15–23:15 `+1`；23:15–24:00 `0` |
| 早起窗口 | 06:00 – 12:00 |
| 早起档位 | 06:00–09:00 `+1`；09:00–12:00 `0` |
| 漏打 | 窗口关闭后 `-1`，可申诉 |
| 月度全勤 | 一个月内两项都打卡 ≥22 天 → `+10`（打满第 22 天当场发，每月一次） |
| 同步奖 | 默认 `0`（关闭）；`syncBonus=1` 可开 |
| 爱心下限 | 0，扣到 0 封顶 |
| 规则修改 | 必须对方同意，只影响之后的打卡 |

### 9.2 两个「日期」概念（最容易搞错）

| 概念 | 变量 | 用途 |
|---|---|---|
| **真实时间** | `ctx.now` | 判断「现在能不能打卡、能拿几分」（窗口 + 档位） |
| **打卡日** | `dayKey` | 记录归属（中午 12 点前算前一天，因为那是同一晚） |

```
cutoverHour = 12 时：

10-26 22:30 早睡   → 真实时间 10-26 22:30，打卡日 10-26
10-27 06:40 早起   → 真实时间 10-27 06:40，打卡日 10-26   ← 同一晚！
10-27 11:59 早起   → 打卡日 10-26
10-27 12:00 早起   → 打卡日 10-27
11-01 06:00 早起   → 打卡日 10-31   ← 算进 10 月日历
```

**没有这个设计会怎样**：早睡在 D 日、早起在 D+1 日，两项永远不在同一个日期上，
「全勤」「连续天数」「月度 22 天」永远不成立。

代码在 `shared/checkin-rules.js` 的 `sleepDayKey(ms, cfg)`：

```js
function sleepDayKey(ms, cfg) {
  const c = cfg || DEFAULTS
  const p = clock.parts(ms)
  const key = clock.dateKey(ms)
  if (typeof c.cutoverHour === 'number' && p.h < c.cutoverHour) {
    return clock.shiftKey(key, -1)
  }
  return key
}
```

**切分点不是随便填的**：必须落在「没有打卡活动的空档」里（早起结束后、早睡开始前）。
否则日期会整体偏移。校验器 `validateConfig` 会强制：

```js
if (!(wakeEnd <= cutHour && cutHour <= sleepStart)) {
  errors.push({ field: 'cutoverHour', message: '打卡日切分点必须落在 ... 之间' })
}
```

### 9.4 数据模型 `checkins`

| 字段 | 类型 | 说明 |
|---|---|---|
| `openid` | string | 谁打的 |
| `coupleId` | string | 哪段关系（**所有查询都必须带**） |
| `date` | string | 打卡日 `YYYY-MM-DD` |
| `type` | string | `sleep` / `wake` |
| `at` | number | 真实打卡时间戳（毫秒） |
| `hearts` | number \| null | 这一项拿了多少（0 也要记） |

**为什么 0 分档也要记一条**：

- 全勤统计只看「有没有打卡」，不看分数；
- 去重也要靠这条记录。

### 9.5 打卡一次，服务端到底做了什么

入口：`cloudfunctions/api/modules/checkin/index.js:184` 的 `act(ctx, payload)`。

```js
async function act(ctx, payload) {
  const cfg = cfgOf(ctx)

  // ① 校验类型
  const type = payload.type
  const meta = rules.LABELS[type]
  if (!meta) return respond.biz('BAD_TYPE', '没有这个打卡项')

  // ② 窗口判定（服务器时间）
  const state = rules.windowState(type, ctx.now, cfg)
  if (state === 'upcoming') return respond.biz('NOT_YET', '...开放（云端现在 ...）')
  if (state === 'expired')  return respond.biz('CLOSED', '窗口已结束')

  // ③ 打卡日（不是自然日）
  const dayKey = dayKeyOf(ctx)

  // ④ 去重：这一天这一项只能打一次
  if (await store.countType(ctx, ctx.openid, dayKey, type)) {
    return respond.biz('DUP', '这一晚已经打过卡啦')
  }

  // ⑤ 算档位奖励
  const heartsAt = rules.heartsAt(type, ctx.now, cfg)
  const base = typeof heartsAt === 'number' ? heartsAt : 0

  // ⑥ 先写业务记录（0 分也写）
  await store.add(ctx, dayKey, type, base)

  // ⑦ 再发爱心（只发 >0 的）
  const records = await todayRecords(ctx)
  const reasons = []
  let total = 0
  if (base > 0) {
    await ctx.award(base, meta.label + '打卡', { refId: dayKey })
    total += base
    reasons.push(meta.label + '打卡 +' + base)
  } else {
    reasons.push(meta.label + '打卡（这一档没有爱心）')
  }

  // ⑧ 同步奖（默认关闭）
  if (cfg.syncBonus > 0 && ctx.partner) {
    const partnerDone = (await store.countType(ctx, ctx.partner.openid, dayKey, type)) > 0
    if (partnerDone) {
      await ctx.award(cfg.syncBonus, '同步' + meta.label, { refId: dayKey })
      total += cfg.syncBonus
      reasons.push('同步' + meta.label + ' +' + cfg.syncBonus)
    }
  }

  // ⑨ 月度全勤（幂等）
  if (records.sleep && records.wake) {
    const days = await store.getMonth(ctx, dayKey.slice(0, 7))
    const fullCount = rules.countFullDays(days)
    if (rules.monthlyReached(fullCount, cfg)) {
      const month = dayKey.slice(0, 7)
      const got = await ctx.award(cfg.monthly.bonus, '月度全勤 ' + month, {
        idemKey: 'monthly:' + month
      })
      if (got) { total += got; reasons.push('月度全勤（' + fullCount + ' 天） +' + got) }
    }
  }

  // ⑩ 返回奖励 + 最新详情 + 连续天数
  return {
    reward: { delta: total, reasons },
    detail: await detail(ctx),
    streak: rules.calcStreak(await fullDayKeys(ctx), dayKey)
  }
}
```

逐步解释：

| 步 | 关键点 | 为什么 |
|---|---|---|
| ① | 白名单类型 | 防止传 `type=hack` |
| ② | **服务器时间**判定 | 手机时间可随便改，服务端时间不可伪造 |
| ③ | `dayKey` 而非 `dateKey` | 凌晨的早起要归到前一晚 |
| ④ | 先查再写 | 防连点；客户端 `busy` 只是第一道 |
| ⑤ | `heartsAt` 返回 `null`（不在窗口）或数字（档位分） | 0 也要区分「打了但 0 分」 |
| ⑥ | 先落业务记录 | 即使后面发爱心失败，至少知道「他打过卡」 |
| ⑦ | 只有 `>0` 才写流水 | 0 分不产生无意义的 `+0` |
| ⑧ | 同步奖读对方记录 | `ctx.partner` 由内核给，模块不查 profile |
| ⑨ | 全勤在「打满那天」发 | 不用等月底；`idemKey` 保证每月一次 |
| ⑩ | 返回 `detail` | 前端一次请求就能刷新整页，不用再拉一次 |

### 9.6 窗口与档位的数学

```js
// 窗口状态：'upcoming' | 'open' | 'expired'
function windowState(type, ms, cfg) {
  const t = cfg[type]
  const cur = clock.dayMinutes(ms)          // 今天第几分钟
  if (cur < clock.minutesOf(t.window.start)) return 'upcoming'
  if (cur >= clock.minutesOf(t.window.end)) return 'expired'
  return 'open'
}

// 档位：左闭右开
function tierAt(type, ms, cfg) {
  const cur = clock.dayMinutes(ms)
  for (const tier of cfg[type].tiers) {
    if (cur >= minutesOf(tier.from) && cur < minutesOf(tier.to)) return tier
  }
  return null
}
```

例子（默认规则）：

| 时刻 | `windowState('sleep')` | `heartsAt('sleep')` |
|---|---|---|
| 21:29 | upcoming | null |
| 21:30 | open | 2 |
| 22:14 | open | 2 |
| 22:15 | open | 1（左闭右开） |
| 23:14 | open | 1 |
| 23:15 | open | 0 |
| 23:59 | open | 0 |
| 00:00（次日） | upcoming | null（新的一天，但早睡窗口还没开） |

> 注意：`24:00` 不是合法时刻，但配置里允许写 `24:00` 表示「当天结束」。
> `minutesOf('24:00') = 1440`，`dayMinutes` 最大 1439，所以「`cur >= 1440`」永远不成立，
> 窗口会一直开到 23:59:59。这是刻意的。

### 9.7 去重：三层防线

| 层 | 机制 | 位置 |
|---|---|---|
| 客户端 | `this.busy`，请求期间不响应第二次点击 | `pages/m/checkin/index.js:171` |
| 服务端业务 | 查 `checkins` 是否已有 `(openid, coupleId, dayKey, type)` | `modules/checkin/index.js:207` |
| 服务端账本 | 发爱心时带 `refId`（但不带 `idemKey`；靠上面的业务查重） | `index.js:221` |

> 这里发爱心**没有**用 `idemKey`，而是靠「业务记录唯一」来保证只发一次。
> 如果以后有人绕过 `act` 直接发奖，就可能重复。更稳的做法是给打卡奖励也加
> `idemKey: 'checkin:<type>:<day>'`，但要注意「改规则后补发」等场景。当前设计够用。

### 9.8 奖励的三种来源

| 奖励 | 触发 | 金额 | 幂等 |
|---|---|---|---|
| 单项打卡 | `act` | 档位配置（2/1/0） | 业务记录唯一 |
| 同步奖 | `act`，对方也打了同一项 | `syncBonus`（默认 0） | 业务记录唯一 |
| 月度全勤 | `act`，当天两项齐，且本月全勤 ≥ 门槛 | `monthly.bonus`（默认 10） | `idemKey = monthly:<月>` |

**同步奖为什么默认关**：
规则 v2 里没有这一项；保留开关是为了以后想开时「改配置就行，代码不用动」。
开法：`core_settings.patch.syncBonus = 1`，或改 `shared/checkin-rules.js` 的 `DEFAULTS.syncBonus`。

> ⚠ 当前实现只在**后完成的人**打卡时给奖励；先完成的人不会补发。
> 所以「两人各 +1」实际不对称。默认关闭时无影响，开启前先修 T75。

### 9.9 漏打结算：定时器 + 惰性 + 幂等

#### 为什么需要结算

「24:00 没打卡就扣 1」不是用户点出来的，是**时间到了**触发的。
云函数无状态、被调用才运行，没有常驻进程。

#### 双保险

```
① 定时触发器：config.json 的 settleHourly，每小时第 5 分钟
      → scheduler.runAll → 每个模块的 actions.settle
② 惰性补算：summary / detail 里也会调一次 settle
      → 打开首页或打卡页时，顺手把漏打补扣
③ 幂等键：idemKey = 'miss:<type>:<打卡日>'
      → 无论跑多少次，只扣一次
```

#### `settle` 代码（`index.js:66`）

```js
async function settle(ctx) {
  const cfg = cfgOf(ctx)
  const today = dayKeyOf(ctx)
  const penalized = []

  // 不结算「配对之前」的日子
  const since = ctx.couple && ctx.couple.pairedAt
    ? rules.sleepDayKey(ctx.couple.pairedAt, cfg)
    : ''

  for (const day of recentDayKeys(today, SETTLE_DAYS + 1)) {   // 最近 4 个打卡日
    if (since && day < since) continue
    for (const type of rules.TYPES) {
      const t = cfg[type]
      if (!t || !t.missPenalty) continue
      if (!rules.windowClosed(day, type, cfg, ctx.now)) continue   // 还没关窗
      if (await store.countType(ctx, ctx.openid, day, type)) continue  // 打了

      const amount = await ctx.penalize(t.missPenalty, label + '漏打 ' + day, {
        idemKey: 'miss:' + type + ':' + day,
        refId: day
      })
      if (amount) penalized.push({ day, type, amount })
    }
  }
  return { penalized }
}
```

#### 窗口什么时候算「关闭」

`rules.windowCloseMs(dayKey, type, cfg)` 的规则：

| 打卡日 D 的窗口 | 关闭的真实时刻 |
|---|---|
| 早睡 21:30–24:00 | **D+1 00:00** |
| 早起 06:00–12:00 | **D+1 12:00** |

推导：`window.end` 的分钟数如果 `<= cutoverHour * 60`，说明这个窗口落在 D+1 的上午；
否则落在 D 的晚上。

```js
const endMin = minutesOf(t.window.end)
const cutMin = cutoverHour * 60
const offset = endMin <= cutMin ? 1 : 0     // 早起 → 1；早睡 → 0
```

#### 结算时机表

| 对象 | 什么时候确定缺卡 | 谁触发 |
|---|---|---|
| 打卡日 D 的早睡 | D+1 00:00 之后 | 定时器 / 惰性 |
| 打卡日 D 的早起 | D+1 12:00 之后 | 定时器 / 惰性 |
| 月度全勤 | 「打满第 22 天」那一刻（不是月底） | `act` 里即时发 |

#### 边界：刚配对不扣历史

`since = sleepDayKey(couple.pairedAt)`，早于配对日的打卡日直接跳过。
否则刚配对就会被倒扣一堆历史，体验极差。

#### 已知问题

- 余额为 0 时 `penalize` 返回 0、不写流水 → 幂等键没落库 → 之后有爱心时可能补扣（窗口 3 天内）。
- `missedList`（页面上的漏卡卡片）不区分「已扣 / 未扣 / 已申诉成功」，统一显示「已扣 N 爱心」。
  申诉通过后卡片仍在，直到移出 4 天窗口。这是产品层的待改进项。

### 9.10 缺卡申诉：从按钮到退分

#### 前端

打卡页的 `misses` 列表（服务端 `missedList` 返回）渲染成橙色卡片：

```
🌙 早睡漏打 · 2026-10-24
已扣 1 爱心                    [说明一下]
```

点「说明一下」→ `wx.showModal({ editable: true })` 输入理由 → `checkin.appeal(dayKey, type, reason)`。

#### 服务端 `appeal`（`index.js:293`）

```
1. type 合法
2. dayKey 格式 YYYY-MM-DD
3. 必须已配对
4. 该项开了 allowAppeal
5. 窗口已关闭（还没结束就先去打卡）
6. 这一天这一项确实没打
7. 没超过申诉截止时间
8. 理由至少 2 个字
9. approvals.create({
     module: 'checkin',
     type: 'late_night' | 'late_wake',
     refId: dayKey + ':' + type,
     toOpenid: ctx.partner.openid,
     payload: { dayKey, type, penalty, reason }
   })
```

#### 对方审批

`approvals.decide` → `onDecision.late_night` → `refundIfApproved`：

```js
const got = await hearts.apply(
  { openid: ticket.fromOpenid, coupleId: env.coupleId },
  [{
    delta: amount,
    reason: '申诉通过退回（' + dayKey + ' ' + label + '）',
    refId: dayKey,
    idemKey: 'appeal:' + ticket._id
  }],
  { now: env.now, ... }
)
```

**注意**：退回是「新增一条正向流水」，不是删掉原来的 `-1`。
原扣分记录保留，历史可查；余额 = 所有流水之和仍然成立。

> ⚠ 当前 `amount` 来自 `payload.penalty`（配置的扣分值），**不是实际扣款额**。
> 如果当时余额为 0、根本没扣，申诉通过仍会退一笔，等于凭空得爱心。修复见 T76。

#### 申诉截止时间

`appealDeadlineMs(dayKey, type, cfg)`：

- 早睡：窗口 D+1 00:00 关闭，截止 `appealDeadline`（默认 12:00）→ D+1 12:00；
- 早起：窗口 D+1 12:00 关闭，截止默认 `24:00` → D+2 00:00。

### 9.11 改规则：提案 → 审批 → 生效

```
打卡页 ⋯ → 修改打卡规则 → 规则编辑页
  → 本地 validateConfig
  → checkin.proposeConfig(完整 config)
  → approvals.create({ type:'rules_change', payload:{ config } })
  → 对方「消息申请」点同意
  → onDecision.rules_change → settings.save(coupleId, 'checkin', config)
  → 从这一刻起的新打卡按新规则；已发爱心不回滚
```

为什么存**完整快照**而不是差异：
- 同意后规则长什么样完全可预期；
- 不会因为以后改默认值而悄悄影响已配置内容；
- `history[]` 保留每次快照，结算历史日期时能取「那天生效的版本」。

### 9.12 `summary` / `detail` / `history`

| action | 谁用 | 返回 | 是否顺手结算 |
|---|---|---|---|
| `summary` | 首页宫格 | `{ todayDone, todayTotal, streak, sub }` | ✅ |
| `detail` | 打卡页 | `{ streak, today, recent, month, calendar, misses, config }` | ✅ |
| `history` | 记录页（当前 UI 未调用） | `{ month, days, stats, logs, hearts }` | ❌ |
| `settle` | 定时器 / summary / detail | `{ penalized: [...] }` | — |

**为什么 `summary` 只返回几个数字**：
首页要同时问多个模块，不能每个都返回整页数据。这是「外壳轻」的关键。

### 9.13 当月日历：服务端拼数据，前端只画格子

服务端 `store.getMonthBoth(ctx, month, partnerOpenid)` 返回：

```js
{
  '2026-10-26': {
    me:      { sleep: 2, wake: 1 },    // 分数；null = 没打
    partner: { sleep: 1, wake: 0 }     // 0 = 打了但 0 分档
  }
}
```

前端 `levelOf(slot)` 把一格压成 0~3：

| level | 含义 | 样式 |
|---|---|---|
| 0 | 没打 / 不存在 | 空白 |
| 1 | 只打了一项 | 细线 |
| 2 | 两项都打，但总分 0 | 半透 |
| 3 | 两项都打，且总分 >0 | 实心 |

日历按**打卡日**归属，所以 11-01 早上的早起会显示在 10-31 那格。
周一为第一列：`lead = (firstDayOfWeek + 6) % 7`。

### 9.14 打卡页前端的三个细节

#### ① 服务器时间偏移

```js
self.offset = (d.serverNow || Date.now()) - Date.now()
// 之后每秒
var now = Date.now() + self.offset
```

手机时间和服务器时间可能差几十秒。用偏移量校准，倒计时才不会和「打卡被拒」打架。
**但真正的判定永远在服务端**，客户端只是显示。

#### ② 每秒重绘

`setInterval` 每秒调 `render()`，重算 `items` 的 `hint` 和 `canCheck`。
离开页面（`onHide` / `onUnload`）必须 `clearInterval`，否则后台还在跑。

#### ③ 打卡成功后重拉整页

```js
checkinApi.act(type).then(res => {
  showFloat(res.reward.delta, res.reward.reasons)
  self.load()          // 日历、连续天数、漏卡列表都可能变
})
```

不自己在前端改状态，避免「前端算的」和「服务端算的」不一致。

### 9.15 规则编辑页的联动与校验

| 操作 | 联动 |
|---|---|
| 改窗口开始 | 第一档的 `from` 跟着改 |
| 改窗口结束 | 最后一档的 `to` 跟着改 |
| 改某档结束 | 下一档的 `from` 跟着改 |
| 改 `cutoverHour` | 不联动，但提交时校验必须落在空档 |

校验器 `validateConfig` 拦的坑：

| 规则 | 错误示例 |
|---|---|
| 时间格式 `HH:mm` | `9:00` 不合法（要 `09:00`） |
| 窗口时间 5 分钟整数倍 | `21:32` |
| 开始早于结束 | `23:00–21:00` |
| 至少一档 | `tiers: []` |
| 最多 8 档 | 9 档 |
| 第一档从窗口开始 | `21:30` 窗口，第一档 `21:40` |
| 最后一档到窗口结束 | `24:00` 窗口，最后一档 `23:00` |
| 档位首尾相接 | 第一档到 22:15，第二档从 22:20 |
| 每档开始早于结束 | `22:15–22:15` |
| 爱心 0~10 整数 | `-1`、`2.5`、`11` |
| 缺卡扣分 0~5 整数 | `6` |
| 申诉截止 `HH:mm` | `中午` |
| 全勤天数 1~31 | `0`、`32` |
| 全勤奖励 0~100 | `101` |
| `cutoverHour` 在空档 | 填 `23:00`（晚于早睡 21:30）或 `06:00`（早于早起结束 12:00） |

> `cutoverHour` 的校验条件是 `wakeEnd <= cut <= sleepStart`。
> 默认早起 12:00、早睡 21:30，所以 12:00–21:30 都合法；但业务上建议 12（中午）。

### 9.16 `store.js`：为什么每条查询都带 `coupleId`

```js
.where({ openid: ctx.openid, coupleId: ctx.coupleId, date: dateKey })
```

如果只按 `openid`：
- 和 A 连续 30 天 → 解绑 → 和 B 配对 → 连续天数继承 30 天；
- 旧关系的日历会串到新关系。

`coupleId` 是「这段关系」的隔离键。解绑后旧数据封存在旧 `coupleId` 下，新关系看不到。

| 函数 | 查询 | 用途 |
|---|---|---|
| `getRecords(ctx, dateKey)` | openid + coupleId + date | 今天两项的状态 |
| `countType(ctx, openid, date, type)` | + type | 去重 / 判断对方打没打 |
| `add(ctx, date, type, hearts)` | — | 写一条 |
| `getFullDayKeys(ctx, today, 60)` | 最近 60 天 | 连续天数 |
| `getMonth(ctx, month)` | 本月我的 | 全勤统计 |
| `getMonthBoth(ctx, month, partner)` | 本月两人 | 日历 |

### 9.17 边界案例表

| 场景 | 期望 | 代码怎么保证 |
|---|---|---|
| 23:59 打早睡 | 可以，0 分 | `windowState` 用 `< end`，24:00 才关 |
| 00:00 打早睡 | 不可以，等明天 21:30 | 新的一天，`cur=0 < start` → upcoming |
| 次日 06:00 早起 | 归到前一天，和昨晚早睡同一打卡日 | `sleepDayKey` 的 cutover |
| 次日 12:00 早起 | 窗口关闭，归到当天（打卡日 D+1） | `cur >= 720` → expired |
| 11-01 06:00 早起 | 打卡日 10-31，算进 10 月 | `shiftKey(-1)` |
| 改窗口后旧记录 | 不受影响，分数在打卡时已写死 | `checkins.hearts` 存了当时分数 |
| 改规则后结算旧日期 | 期望按「那天生效的规则」；当前 `settle` 用的是 `ctx.config`（当前规则） | `settings.configAt` 已写好但未接入（T39） |
| 配对前漏打 | 不扣 | `since = pairedAt` |
| 解绑后看旧日历 | 看不到 | 新 `coupleId` |
| 同一天打两次 | 第二次 `DUP` | `countType` |
| 余额 0 时漏打 | 不扣，不写流水 | `penalize` 返回 0 |
| 申诉通过 | 退分，原扣分保留 | 反向流水 + `appeal:<ticket>` |

### 9.20 打卡问题排查清单

| 漏打没扣分 | 定时器部署了吗？余额是不是 0？`pairedAt` 之后吗？ |
| 扣了两次 | 查 `heart_logs` 里 `idemKey=miss:...` 有几条 |
| 申诉通过没退分 | 工单 `applied` 有没有 error？`appeal:<ticket>` 流水在吗？ |
| 改规则没生效 | 对方同意了吗？`core_settings` 里 `patch` 更新了吗？ |
| 页面时间和手机不一致 | 正常，用的是服务器偏移 |

## 十、消息通知系统

### 10.1 先说实话：现在没有「推送」

当前项目**没有**接入微信订阅消息，也没有任何后台推送。
你收到的「消息」只有一种：**打开小程序 → 我的 → 消息申请**，里面是待处理的工单。

```
我的页
  └─ 消息申请  [2]   ← 红色数字是 toMe.length（待我处理）
       ├─ 待我处理：晚睡说明 / 晚起说明 / 修改打卡规则
       └─ 我发起的：等对方处理 / 已同意 / 已拒绝
```

所以「消息通知」目前是**站内信 + 红点**，不是手机弹窗。

### 10.2 现有站内消息的完整链路

```
A 提交申诉
  → checkin.appeal
  → approvals.create({ toOpenid: B, status: 'pending' })
  → A 的页面提示「已发给 TA」
  → B 打开小程序 → 我的 → 消息申请
  → approvals.list 返回 { toMe: [...], mine: [...] }
  → B 点同意 → approvals.decide
  → onDecision.late_night → 退分
  → A 下次打开打卡页，看到爱心回来了
```

**局限**：
- B 不打开小程序就永远不知道；
- 没有「已读/未读」，只有 pending 数量；
- 没有推送，也没有短信。

### 10.3 微信订阅消息是什么（给第一次做小程序的人）

微信不允许小程序随便给用户发消息。必须满足：

1. **用户主动授权**：在用户点击的交互里调 `wx.requestSubscribeMessage`；
2. **一次性订阅**：用户同意一次，你只能发一条（「长期订阅」只对特定行业开放，个人工具类基本拿不到）；
3. **模板审核**：在微信公众平台选/申请模板，拿到 `templateId`；
4. **内容受限**：模板里的字段名、类型、长度都是固定的（`thing` 20 字以内、`time` 时间格式等）；
5. **发送在服务端**：云函数用 `cloud.openapi.subscribeMessage.send`。

> 结论：不能做「每天 21:30 无条件推送」。只能做「用户点过『提醒我』→ 我们在他授权的那一次额度内发一条」。
> 想每天提醒，只能每天让用户点一次授权（体验很差），或者改用「服务通知」以外的方式（邮件/短信，成本高）。
> 这是产品设计必须先接受的约束。

### 10.4 建议的 `notify` 设计（尚未实现）

**定位**：内核服务，只放「通道」，不放内容。
模板、文案、触发时机属于各模块。

```js
// core/notify.js（规划）
notify.send(openid, templateKey, data, opts)
// opts: { page, idemKey, miniprogramState }
```

| 部分 | 放哪 | 说明 |
|---|---|---|
| 模板 ID / 字段映射 | `core/notify-templates.js` 或环境配置 | 一个 `templateKey` 对应一个 `templateId` + 字段转换 |
| 频控 / 去重 | `notify.send` 内部 | 同一 `idemKey` 只发一次；每人每天每类最多 1 条 |
| 发送记录 | `core_notify_logs` | 审计、排查、防重复 |
| 业务触发 | 各模块 | 打卡提醒、审批提醒、全勤奖励 |

建议的数据表：

```
core_notify_logs
  openid, templateKey, refId, idemKey,
  page, payload, status: 'sent' | 'failed' | 'skipped',
  errMsg, createdAt
```

### 10.5 哪些时机值得发

| 时机 | 触发方 | 模板示例 | 频控 |
|---|---|---|---|
| 21:30 还没早睡打卡 | 定时任务 / 打卡模块 | 「该睡啦，今晚还没打卡」 | 每天 1 次 |
| 收到新工单 | `approvals.create` 后 | 「TA 提交了晚睡说明，等你处理」 | 每张工单 1 次 |
| 工单被处理 | `approvals.decide` 后 | 「你的申诉通过了」 | 每张工单 1 次 |
| 月度全勤达成 | 打卡 `act` 发奖后 | 「本月全勤达成，+10 爱心」 | 每月 1 次 |
| 对方打卡了 | 打卡 `act` | 不建议（会变成骚扰） | — |

**不要做的**：
- 每天多条；
- 深夜发；
- 把「对方没打卡」当成提醒理由（会变成互相监督的压力）；
- 用订阅消息做营销。

### 10.6 实现步骤（按顺序）

**第 1 步 · 配模板**

微信公众平台 → 订阅消息 → 选用模板（如「打卡提醒」「审批提醒」），记下 `templateId` 和字段名。

**第 2 步 · 云函数声明权限**

```json
// cloudfunctions/api/config.json
{
  "permissions": { "openapi": ["subscribeMessage.send"] },
  "triggers": [ ... ]
}
```

**第 3 步 · 前端请求授权（必须在用户点击里）**

```js
// pages/m/checkin/index.js（示例，尚未接入）
askRemind: function () {
  wx.requestSubscribeMessage({
    tmplIds: ['<模板ID>'],
    success: function (res) {
      if (res['<模板ID>'] === 'accept') {
        // 告诉服务端「他同意了」，服务端记下来（可选）
        wx.showToast({ title: '会提醒你', icon: 'success' })
      }
    },
    fail: function (err) {
      console.warn('订阅失败', err)
    }
  })
}
```

**第 4 步 · 服务端发送（示例）**

```js
// core/notify.js（规划）
const cloud = require('wx-server-sdk')
const { db } = require('./db.js')

async function send(openid, templateKey, data, opts) {
  const tpl = TEMPLATES[templateKey]
  if (!tpl) throw new Error('未知模板：' + templateKey)

  // 幂等：同一件事只发一次
  if (opts.idemKey) {
    const dup = await db.collection('core_notify_logs')
      .where({ openid, idemKey: opts.idemKey }).count()
    if (dup.total > 0) return { skipped: true }
  }

  try {
    const res = await cloud.openapi.subscribeMessage.send({
      touser: openid,
      templateId: tpl.id,
      page: opts.page || 'pages/home/home',
      data: tpl.format(data),
      miniprogramState: opts.miniprogramState || 'formal'
    })
    await db.collection('core_notify_logs').add({ data: { ... } })
    return { sent: true, res }
  } catch (err) {
    await db.collection('core_notify_logs').add({ data: { ... status: 'failed', errMsg: err.message } })
    return { sent: false, error: err.message }
  }
}
```

**第 5 步 · 接一个最简单的场景**

建议先做「审批提醒」，不要先做打卡提醒：
- 触发点明确（`approvals.create` 之后）；
- 用户价值高（对方能及时处理）；
- 不依赖定时器；
- 频控简单（每张工单一条）。

**第 6 步 · 验收**

- 用户点「提醒我」→ 授权 → 对方提交申诉 → 收到一条；
- 同一张工单只收到一条（`idemKey`）；
- 用户拒绝授权 → 不报错，走站内红点；
- 模板字段不匹配 → 日志里有 `errCode`，页面不受影响。

### 10.7 通知的降级策略

| 情况 | 行为 |
|---|---|
| 用户没授权 | 不发；站内红点仍然工作 |
| 一次性额度用完 | 发送失败；记录 `failed`；不重试轰炸 |
| 模板被下架/字段变更 | 发送失败；记录；不阻塞业务 |
| 云函数 openapi 权限没配 | 发送失败；日志提示去 `config.json` 加权限 |
| 体验版 | `miniprogramState: 'trial'`，否则用户点不开 |

### 10.8 通知的合规红线

- 订阅消息必须用户主动授权，不能诱导、不能默认勾选；
- 不能发与模板无关的内容；
- 不能高频骚扰；
- 个人主体能用的模板有限，选不到就换产品方案（站内信/邮件），**不要买第三方推送**。

## 十三、新手 FAQ

**Q1：为什么小程序里不能直接连数据库？**
可以连，但本项目故意把集合权限设为「所有用户不可读写」。这样所有判定和记账都在云函数里，手机改时间也没用。客户端只能 `callFunction`。

**Q2：为什么云函数只有一个？不是应该一个功能一个函数吗？**
云开发每个函数都要单独部署、单独配环境、各自冷启动。两个人用的项目，一个函数 + 内部模块化成本最低。真慢了再拆，路由协议不用改。

**Q3：为什么 `rules.js` 有四份？**
小程序代码包只能包含 `miniprogram/`，云函数部署只打包自己的目录，两边都引用不到仓库根的 `shared/`。所以 `shared/` 是唯一真相，其余是生成物。改规则只改 `shared/`。

**Q4：为什么打卡日不是自然日？**
早睡在 D 日晚上、早起在 D+1 日早上，如果按自然日，两项永远不在同一天，全勤永远不成立。中午 12 点切分让它们归到同一「晚」。

**Q5：为什么爱心不能为负？**
「你欠我 30 爱心」会变成吵架素材，兑换逻辑也要处理负数。扣到 0 封顶最省事。

**Q6：为什么解绑要写反向流水，不直接把余额改 0？**
直接改 0 会让「余额 = 流水之和」永久破裂，历史查不出来。反向流水既清零又保留历史。

**Q7：为什么我改了代码，对象那边没变化？**
小程序界面要「上传 + 设为体验版」；云函数要「上传并部署」。两者是分开的。而且对象需要杀掉小程序重进（或清缓存）。

**Q8：为什么体验版和正式版数据一样？**
它们共用同一个云环境。这是特性也是风险：改数据会立刻影响对方。

**Q9：本地预览模式能用来测试规则吗？**
只能看界面。它用手机时间、不结算、不能真配对/审批。规则正确性以 `smoke-test` / `cloud-test` 为准。

**Q10：为什么打卡按钮有时候显示「未开放」，但我的手机时间是对的？**
判定用服务器时间。可能是云函数时区/规则窗口问题；看页面上的「云端现在」时间和规则明细。

**Q11：为什么漏打没有立刻扣分？**
早睡要等次日 00:00 窗口关闭，早起要等次日 12:00；然后等定时器（每小时 :05）或你下次打开小程序（惰性结算）。

**Q12：为什么申诉通过了，漏卡卡片还在？**
当前 `missedList` 只看「有没有打卡记录」，不看「是否已退款/已申诉」。卡片会保留到移出最近 4 天窗口。这是已知的产品待改进项。

**Q13：为什么余额 0 时漏打没有流水？**
`penalize` 在余额 0 时直接返回，不写流水。设计文档原本要求写一条「已归零」记录，当前未实现。影响很小，但已记入待办。

**Q14：我能自己加一个页面吗？**
可以。在 `miniprogram/pages/` 建四件套，在 `app.json` 的 `pages` 里注册。如果是功能模块，再按第九节第 9.2 的 9 步走。

**Q15：我想把项目给别的 AI 接手，先给它看什么？**
先看 [`../module-dev/项目交接.md`](../module-dev/项目交接.md)，再看本文的第二节（代码地图）和第八、九节（幂等/打卡）。交接文档里有「启动 prompt 模板」。
