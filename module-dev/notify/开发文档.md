# 消息通知（notify）· 开发文档

> 定位：**内核服务**（不是业务模块） ｜ 状态：⬜ 规划（**尚未实现**）
> 规则见 [`规则文档.md`](规则文档.md)；现有站内消息见 [`../../docs/代码详解.md`](../../docs/代码详解.md) 第十节。

---

## 一、先说实话：现在没有推送

当前项目**没有**接入微信订阅消息，也没有后台推送。
唯一的「消息」是**站内工单**：

```
我的 → 消息申请 [2]
  ├─ 待我处理：晚睡说明 / 晚起说明 / 修改打卡规则
  └─ 我发起的：等对方处理 / 已同意 / 已拒绝
```

红色数字是 `approvals.list().toMe.length`，不是系统推送。
对方不打开小程序，就不知道有申请。

---

## 二、为什么通知算「内核」而不是「模块」

按 [`../../docs/系统架构.md`](../../docs/系统架构.md) 9.3 的准入五问：

1. 每个模块都可能要发通知？→ 是（打卡提醒、审批提醒、商城兑现提醒）。
2. 必须唯一？→ 是（频控、去重、发送记录必须集中，否则会轰炸）。
3. 必须原子？→ 发送记录 + 去重要一致。
4. 形状稳定？→ `send(openid, templateKey, data)` 很稳定。
5. 名词还是流程？→ 它是「通道」，不是业务；模板和文案归模块。

**结论**：内核只放「通道 + 频控 + 去重 + 发送记录」，**不放模板内容**。

|---|---|---|

本文只讨论小程序订阅消息。

## 四、微信订阅消息的硬约束（先接受再设计）

| 约束 | 含义 |
|---|---|
| 用户主动授权 | 必须在用户点击的交互里 `wx.requestSubscribeMessage`，不能静默请求 |
| 一次性订阅 | 用户同意一次，只能发一条（长期订阅只对特定行业开放） |
| 模板审核 | 模板 ID + 字段名/类型/长度固定，不能自由发挥 |
| 服务端发送 | 云函数 `cloud.openapi.subscribeMessage.send` |
| 不能保证到达 | 用户可能拒收、额度用完、模板下架 |

> **最重要的一条**：不能做「每天晚上 21:30 无条件推送」。
> 用户只授权一次，就只能发一条。想每天提醒，得每天让用户点一次授权（体验差），
> 或者改用公众号模板消息/App 推送（另一个量级）。

**所以产品上要接受**：
- 通知是「锦上添花」，不是「打卡的保证」；
- 站内红点/首页提示仍然是主路径；
- 先做「审批提醒」这种低频、高价值的场景，不要先做每日提醒。

## 五、接口设计

```js
// core/notify.js（规划）
/**
 * @param {string} openid
 * @param {string} templateKey   业务语义 key，如 'approval_new'
 * @param {object} data          模板字段
 * @param {object} opts          { page, idemKey, miniprogramState, refId }
 * @returns {object}             { sent, skipped?, error? }
 */
notify.send(openid, templateKey, data, opts)
```

模板配置（不进内核业务）：

```js
// core/notify-templates.js
module.exports = {
  approval_new: {
    id: 'TEMPLATE_ID_1',
    page: 'pages/approvals/approvals',
    format: (d) => ({
      thing1: { value: d.title },     // 字段名以实际模板为准
      thing2: { value: d.summary },
      time3: { value: d.timeText }
    })
  },
  approval_result: { ... },
  checkin_remind: { ... }
}
```

数据表：

```
core_notify_logs
  _id, openid, templateKey, refId, idemKey,
  page, payload, status: 'sent' | 'failed' | 'skipped',
  errCode, errMsg, createdAt
```

索引：`(openid, idemKey)`（用于去重）、`(openid, templateKey, createdAt)`（用于频控）。

## 六、发送流程

```
业务模块（如 approvals.create）
  → notify.send(toOpenid, 'approval_new', data, {
      page: 'pages/approvals/approvals',
      idemKey: 'notify:approval:' + ticketId,
      refId: ticketId
    })
      ├─ 查 core_notify_logs：同 idemKey 已发 → skipped
      ├─ 查频控：今天同类是否已发 → skipped
      ├─ cloud.openapi.subscribeMessage.send(...)
      ├─ 成功 → 记 sent
      └─ 失败 → 记 failed（不抛给业务，不阻塞审批）
```

**关键**：通知失败不能影响主业务。
打卡成功但提醒没发出去，不能因此让打卡失败。

## 七、触发点（建议顺序）

| 优先级 | 场景 | 触发位置 | 模板 key | 说明 |
|---|---|---|---|---|
| 1 | 有新工单待处理 | `approvals.create` 之后 | `approval_new` | 低频、高价值、易验收 |
| 2 | 工单被处理 | `approvals.decide` 之后 | `approval_result` | 让申请人知道结果 |
| 3 | 月度全勤达成 | 打卡 `act` 发奖后 | `monthly_bonus` | 每月一次，惊喜 |
| 4 | 21:30 还没早睡打卡 | 定时任务 | `checkin_remind` | **受一次性授权限制**，只做「用户刚授权过的那一次」 |
| 5 | 合资订单待对方付款 | `shop.act` 之后 | `shop_split_wait` | 商城上线后 |

**不要做**：
- 对方一打卡就通知（骚扰）；
- 每天多条；
- 深夜发；
- 用「对方没打卡」当提醒理由（制造压力）。

## 八、实现步骤

### 第 1 步 · 配模板

微信公众平台 → 订阅消息 → 选用模板（如「审批提醒」「打卡提醒」），记下：
- `templateId`
- 每个字段的 key 和类型（`thing` / `time` / `number` / `phrase`）
- 字段长度限制（`thing` 通常 ≤20 字）

### 第 2 步 · 云函数权限

```json
// cloudfunctions/api/config.json
{
  "permissions": { "openapi": ["subscribeMessage.send"] },
  "triggers": [ ... ]
}
```

### 第 3 步 · 前端授权（用户点击）

```js
// 示例：审批页/设置页的「提醒我」按钮
requestNotify: function () {
  wx.requestSubscribeMessage({
    tmplIds: ['TEMPLATE_ID_1'],
    success: (res) => {
      if (res['TEMPLATE_ID_1'] === 'accept') {
        wx.showToast({ title: '会提醒你', icon: 'success' })
      }
    },
    fail: (err) => console.warn('订阅失败', err)
  })
}
```

> 授权必须发生在用户点击里；页面 `onLoad` 自动弹会被微信拒绝。

### 第 4 步 · 服务端发送

```js
// core/notify.js（示例，非现有代码）
const cloud = require('wx-server-sdk')
const { db, COL } = require('./db.js')

async function send(openid, templateKey, data, opts) {
  const tpl = require('./notify-templates.js')[templateKey]
  if (!tpl) return { sent: false, error: 'UNKNOWN_TEMPLATE' }

  if (opts.idemKey) {
    const dup = await db.collection('core_notify_logs')
      .where({ openid, idemKey: opts.idemKey }).count()
    if (dup.total > 0) return { sent: false, skipped: true }
  }

  try {
    const res = await cloud.openapi.subscribeMessage.send({
      touser: openid,
      templateId: tpl.id,
      page: opts.page || tpl.page,
      data: tpl.format(data),
      miniprogramState: opts.miniprogramState || 'formal'
    })
    await db.collection('core_notify_logs').add({ data: {
      openid, templateKey, refId: opts.refId || '',
      idemKey: opts.idemKey || '', page: opts.page || tpl.page,
      payload: data, status: 'sent', createdAt: Date.now()
    }})
    return { sent: true, res }
  } catch (err) {
    await db.collection('core_notify_logs').add({ data: {
      openid, templateKey, refId: opts.refId || '',
      idemKey: opts.idemKey || '', page: opts.page || tpl.page,
      payload: data, status: 'failed',
      errCode: err.errCode, errMsg: err.errMsg || err.message,
      createdAt: Date.now()
    }})
    return { sent: false, error: err.errMsg || err.message }
  }
}
```

### 第 5 步 · 接第一个场景

在 `approvals.create` 成功后：

```js
await notify.send(toOpenid, 'approval_new', {
  title: ticket.title,
  summary: ticket.summary,
  timeText: clock.timeKey(Date.now())
}, {
  idemKey: 'notify:approval:' + ticket._id,
  refId: ticket._id
})
```

### 第 6 步 · 验收

- [ ] 用户点「提醒我」→ 授权成功；
- [ ] 对方提交申诉 → 收到一条；
- [ ] 同一张工单只收到一条（idemKey）；
- [ ] 用户拒绝授权 → 不报错，站内红点仍工作；
- [ ] 模板字段超长 → 发送失败，有日志，不影响审批；
- [ ] 体验版能打开（`miniprogramState: 'trial'`）。

## 九、测试

| 测试 | 方法 |
|---|---|
| 幂等 | 同 idemKey 调两次，只发一次（mock openapi） |
| 频控 | 同一天同类第二次 skipped |
| 失败降级 | 模板 ID 错误 → 返回 `{sent:false}`，业务不抛 |
| 日志 | `core_notify_logs` 有 sent/failed 记录 |

## 十、风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 一次性授权 | 不能每天推送 | 产品上接受；先做低频场景 |
| 模板审核不过 | 发不了 | 选常规模板；文案别夸张 |
| 字段超长 | 发送失败 | 服务端截断 + 日志 |
| 用户拒收 | 收不到 | 站内红点兜底 |
| 频控太松 | 骚扰 | 每人每天每类 1 条 |
| 通知失败阻塞业务 | 打卡失败 | try/catch，绝不影响主流程 |
| 体验版状态错误 | 点不开 | `miniprogramState` 按环境传 |
