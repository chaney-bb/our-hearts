## 〇、给 AI 的使用说明（先读这段）

你接手的是一个**两个人的微信打卡小程序**，不是通用 SaaS，不要按「多用户产品」的思路加权限/多租户/微服务。

**开工前必须做**：

1. 读本文 → 读 [`项目待办.md`](项目待办.md) → 读你要改的模块文档；
2. 跑两套测试，确认 141 条全绿；
3. 只做**一个**任务编号，不要顺手重构；
4. 改完跑测试 + 真机点一遍 + 更新本文「当前状态」；
5. 提交信息带任务编号（如 `T33 修余额0时的幂等流水`）。

**绝对不要**：

- 跨模块 `require`；
- 绕过 `ctx.award` / `ctx.penalize` 直接改 `core_wallets`；
- 手改生成物（`utils/rules.js`、`utils/clock.js`、`core/clock.js`、`modules/checkin/rules.js`）；
- 在首页写 `if (key === 'checkin')`；
- 把业务规则写死在代码里（应放 `defaults` + `ctx.config`）；
- 删除 `heart_logs` 里的流水（要修账就写反向流水）；
- 一次改多个模块。

## 五、架构铁律（违反就是事故）

1. **模块只通过 `ctx` 用内核**，不 `require` 另一个模块。
2. **每个模块只读写自己声明的集合**（`collections`），`ctx.db` 会拦。
3. **加功能 = 新目录 + 注册表 1 行**；改了已有模块就是架构失败。
4. **内核只放事实，不放流程**：身份、爱心、时间、审批状态机、配置；提醒/月报/勋章不进内核。
5. **所有写操作必须有防重**：业务唯一记录或 `idemKey`。
6. **爱心只能走 `ctx.award` / `ctx.penalize`**，不许直接改 `core_wallets`。
7. **日期用内核的 `dateKey` / 打卡日 `dayKey`**，不要自己 `new Date()` 拼。
8. **判定用服务器时间 `ctx.now`**，不要信客户端时间。
9. **改规则只改 `shared/`**，然后同步 + 部署。
10. **先部署云函数，再编译小程序**。

## 六、核心概念（不懂这几个就看不懂代码）

| 概念 | 含义 | 代码位置 |
|---|---|---|
| `openid` | 微信用户在本小程序的唯一 id；用户主键 | `identity.getProfile` |
| `coupleId` | 一段关系 id；所有业务数据挂在它上面 | `couples._id` |
| `dateKey` | 北京时间 `YYYY-MM-DD` | `core/clock.js` |
| **打卡日 `dayKey`** | 中午 12:00 前算前一天；早睡 D + 早起 D+1 = 同一晚 | `rules.sleepDayKey` |
| `ctx` | 模块能看到的全部世界 | `core/context.js` |
| `config` | `defaults + core_settings 覆盖`，服务端下发 | `core/settings.js` |
| `heart` / `heart_logs` | 爱心 / 只追加的流水；余额 = 流水之和 | `core/hearts.js` |
| `idemKey` | 幂等键；同一业务只生效一次 | `hearts.apply` |
| 工单 `ticket` | 一方发起、另一方审批；`pending → approved/rejected` | `core/approvals.js` |
| `settle` | 模块的定时结算（漏打扣分） | `modules/checkin/index.js` |
| 模块 `summary` | 给首页宫格的一句摘要，不是整页数据 | `modules/checkin/index.js` |
| 门禁 | 没登记 `NEED_REGISTER`；没配对 `NOT_PAIRED` | `context.create` |

### 6.1 数据模型速查

| 集合 | 作用 | 关键字段 |
|---|---|---|
| `profiles` | 用户资料 | `openid`、`userId`、`realName`、`phone`、`birthday`、`gender`、`bio`、`coupleId` |
| `couples` | 一段关系 | `inviteCode`、`status`、`members[]`、`pairedAt` |
| `core_wallets` | 个人钱包 | `_id = openid`、`balance` |
| `heart_logs` | 爱心流水 | `openid`、`delta`、`reason`、`module`、`refId`、`idemKey` |
| `core_settings` | 规则快照 | `coupleId`、`module`、`patch`、`history[]` |
| `core_approvals` | 工单 | `module`、`type`、`fromOpenid`、`toOpenid`、`refId`、`status`、`payload` |
| `checkins` | 打卡记录 | `openid`、`coupleId`、`date`、`type`、`at`、`hearts` |

### 6.2 三条不变式（测试盯着）

1. `wallet.balance === sum(heart_logs.delta where openid)`
2. `balance >= 0`
3. 同一 `idemKey` 只写一条流水（顺序重试下成立；并发下不保证，见第九节）

## 十、加新模块 SOP（9 步）

> 详细代码模板见 [`../docs/系统架构.md`](../docs/系统架构.md) 9.2。

1. **写边界**：一句话玩法、自有集合、3 个 actions、用内核什么、要不要审批/通知。
2. **服务端建目录**：`cloudfunctions/api/modules/<key>/{index,store,rules}.js`。
3. **写契约**：`key/name/emoji/version/collections/defaults/actions/on/onDecision`。
4. **注册**：`core/registry.js` 加一行 `const MODULES = [checkin, <key>]`。
5. **建集合**：`m_<key>_<实体>`，权限全关。
6. **前端接口层**：`miniprogram/modules/<key>/api.js`。
7. **页面 4 件套**：`pages/m/<key>/index.{js,json,wxml,wxss}` + `app.json` 注册。
8. **前端注册表**：`core/modules.js` 加一条（`enabled: true`）。
9. **测试 + 真机**：新增断言，两套全绿。

**验收**：改动面 = 新增文件 + 两个注册表各 1 行 + `app.json` 1 行；已有模块 0 修改。
**如果发现要改打卡模块 → 停下来修架构，别做功能。**


> 只是你们两个人用，其实**不用改代码**：打卡页 ⋯ → 修改规则 → 对方同意即可。
