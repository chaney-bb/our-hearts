## 一、一句话

两个人花较大一笔钱之前，先在小程序里「报备」一下，对方同意才算数。
本质是**双人审批流**，和打卡那种「单人每日动作」完全不同，正好验证架构撑不撑得住另一种形态。

---

## 二、边界（先划清，避免做成记账 App）

| 做 | 不做 |
|---|---|
| 提交申请（金额/用途/分类） | 接支付、转账、报销 |
| 对方同意/拒绝 | 记真钱流水、改爱心 |
| 本月花费统计 | 预算系统、账单导入、发票 |
| 站内/订阅消息提醒 | 聊天、评论 |

**关键**：消费申请用的是**真钱**，不是爱心。
爱心是打卡/学习这类「努力」的奖励，两者不要混在一起。
这也是为什么这个模块能反过来检验内核边界划得对不对：它**不需要** `hearts`。

## 四、与内核的关系

| 需要 | 用内核的什么 |
|---|---|
| 知道我是谁、对方是谁 | `ctx.me` / `ctx.partner` |
| 按天/按月统计 | `ctx.dateKey` / `ctx.monthKey`（或自己从 dateKey 截） |
| 审批状态机 | `core/approvals`（推荐复用） |
| 通知对方 | `notify`（未实现，先站内红点） |
| 爱心 | **不用** |

> 不要 `require` checkin；不要动 `hearts`；不要往 `core` 塞「消费」这个词。

## 五、数据模型（计划）

```
m_consumption_requests
  _id
  openid            申请人
  coupleId
  amountCents       金额（整数分，避免浮点）
  purpose           用途（2~50 字）
  category          food / transport / shopping / entertainment / other
  status            pending | approved | rejected | cancelled | expired
  needApproval      boolean（<= 阈值时为 false，自动通过）
  reviewerOpenid    审批人
  reviewedAt        审批时间
  ticketId          关联的 core_approvals id（需要审批时）
  note              审批备注
  createdAt / updatedAt
```

索引建议：`(coupleId, createdAt)`、`(openid, status)`。

**为什么用「分」**：`0.1 + 0.2 !== 0.3`。金额一律存整数分，展示时除 100。

## 六、接口（计划）

| action | 入参 | 返回 | 说明 |
|---|---|---|---|
| `consumption.summary` | — | `{ pendingCount, monthTotalCents, sub }` | 首页宫格摘要 |
| `consumption.detail` | — | `{ list, stats, config }` | 列表 + 本月统计 + 配置 |
| `consumption.act` | `{ amountCents, purpose, category }` | `{ request, needApproval }` | 提交申请 |
| `consumption.cancel` | `{ id }` | `{ ok }` | 申请人撤回（仅 pending） |
| `consumption.update` | `{ id, ... }` | `{ ok }` | 可选；建议「撤回重提」 |
| `consumption.settle` | — | `{ expired }` | 惰性过期（可选，或读时判定） |

审批复用系统动作：

```
approvals.list   → 待我处理里出现「消费申请 · ¥128 吃饭」
approvals.decide → onDecision.consumption_request
```

**为什么复用 `core/approvals`**：
- 状态机、谁能审批、防重复提交，内核已经实现；
- 「我的 → 消息申请」不用为每个模块做一套；
- 模块只负责「同意后把 request 标成 approved」。

备选：模块自己维护状态机（更灵活，但要做两套审批 UI）。**不推荐**。

## 八、实施步骤（照抄 P4）

### 第 1 步 · 服务端骨架

```
cloudfunctions/api/modules/consumption/
├─ index.js     契约 + actions
├─ store.js     只碰 m_consumption_requests
└─ rules.js     金额格式、分类、阈值、状态流转
```

### 第 2 步 · 契约

```js
module.exports = {
  key: 'consumption',
  name: '消费申请',
  emoji: '🧾',
  version: 1,
  collections: ['m_consumption_requests'],
  defaults: {
    requireApprovalOverCents: 5000,   // > 50 元才需审批
    maxAmountCents: 10000000,
    categories: ['food', 'transport', 'shopping', 'entertainment', 'other'],
    expireHours: 72
  },
  actions: { summary, detail, act, cancel },
  on: {},
  onDecision: { consumption_request }
}
```

### 第 3 步 · 注册

```js
// core/registry.js
const consumption = require('../modules/consumption/index.js')
const MODULES = [checkin, consumption]
```

### 第 4 步 · 集合

云开发控制台建 `m_consumption_requests`，权限「所有用户不可读写」。

### 第 5 步 · 前端接口层

```js
// miniprogram/modules/consumption/api.js
module.exports = {
  summary: () => api.call('consumption.summary'),
  detail: () => api.call('consumption.detail'),
  act: (data) => api.call('consumption.act', data),
  cancel: (id) => api.call('consumption.cancel', { id })
}
```

### 第 6 步 · 页面 + 注册

`pages/m/consumption/` 四件套；`app.json` 加页面；`core/modules.js` 把 `enabled` 改 `true`。

### 第 7 步 · 测试

至少覆盖：
- 金额 <= 阈值：不用审批，直接 approved；
- 金额 > 阈值：生成工单，对方收到；
- 对方同意 → request approved；拒绝 → rejected；
- 重复提交同一笔（同一 idemKey）→ 拒绝；
- 非 `toOpenid` 审批 → FORBIDDEN；
- 撤回 pending → cancelled；
- 本月统计只算 approved。

## 九、风险与待拍板

| 问题 | 影响 | 建议 |
|---|---|---|
| 金额门槛 50 元 | 太小会烦，太大会失去意义 | 先 50，可在 `defaults` 改 |
| 超时怎么办 | 一直挂着会堆积 | 72h 自动过期（读时惰性） |
| 能不能改已提交的 | 改了对方看到的不一致 | 不能改，撤回重提 |
| 统计口径 | 两人合计还是各算各的 | 两个都显示 |
| 隐私 | 消费记录敏感 | 只双方可见；不上报、不分析 |
| 是否接支付 | 合规红线 | **不接** |
