# 礼物商城模块 · 开发文档

> 模块 key：`shop` ｜ 状态：⬜ 规划（**尚未实现**）
> 规则见 [`规则文档.md`](规则文档.md)；账本设计见 [`../../docs/代码详解.md`](../../docs/代码详解.md) 第七节与 [`../../docs/系统架构.md`](../../docs/系统架构.md) 第六节。

---

## 一、一句话

用爱心换礼物：两个人自己上架礼物（名字、emoji、价格、兑现说明），爱心够就能兑换，生成一张「券」，由对方兑现。

支持**独自购买**（自己付全部）和**合资购买**（各付一半、各点一下）。

---

## 二、边界（很重要）

| 做 | 不做 |
|---|---|
| 礼物上架/下架 | 真钱支付、充值、购买爱心 |
| 独自买 / 合资买 | 实物配送、电商 |
| 生成券、兑现、取消退款 | 抽奖、概率、盲盒 |
| 爱心余额检查、扣款 | 转账给对方的「赠送」 |

**红线**：
- 不做充值、付费买爱心（虚拟货币 + 支付合规，个人主体搞不定）；
- 不做实物交易/配送；
- 爱心只能靠打卡/学习等「努力」获得，**不能买**。

## 三、与内核的关系

| 需要 | 用内核的什么 |
|---|---|
| 我是谁、对方是谁 | `ctx.me` / `ctx.partner` |
| 我的余额 | `ctx.balance()` |
| 扣爱心 | **`hearts.spend` / `hearts.refund`（需要新增内核原语）** |
| 时间 | `ctx.now` / `ctx.dateKey` |

> 商城是**唯一允许调 `ledger.spend`** 的模块。普通模块只能 `ctx.award`（赚），不能扣。
> 但当前 `core/hearts.js` **没有** `spend/refund`，只有 `apply`。所以商城开工前必须先补内核原语（T59）。

### 3.1 需要补的内核接口

```js
// core/hearts.js（计划）
async function spend(openid, coupleId, n, opts) {
  // opts: { module:'shop', reason, refId, idemKey }
  // 1. 读钱包（或事务锁）
  // 2. balance < n → throw INSUFFICIENT
  // 3. 写负向流水 + 更新钱包（必须在同一个事务/原子操作里）
}

async function refund(openid, coupleId, n, opts) {
  // 反向流水，delta = +n，idemKey 防重复
}
```

**不需要**跨用户原子扣款：因为「各付各的」是两次单用户操作，不要求同时成功。
这是当初否决「发起方直接扣双方」后，设计上的简化。

## 四、数据模型（计划）

```
m_shop_gifts
  _id, coupleId,
  name（2~20 字）, emoji, price（1~999 爱心）,
  fulfillment（兑现说明，如「对方洗碗一次」）,
  active（true/false）,
  createdBy（openid）,
  createdAt, updatedAt

m_shop_orders
  _id, coupleId, giftId,
  giftName, giftEmoji, price,          // 快照，防礼物改名/删除
  payerMode: 'single' | 'split',
  payers: [{ openid, amount, paidAt }],  // paidAt=null 表示未付
  fulfillerOpenid,                      // 谁负责兑现
  status: 'pending' | 'paid' | 'fulfilled' | 'cancelled',
  createdAt, paidAt, fulfilledAt,
  cancelledAt, cancelReason
```

**为什么存快照**：礼物以后可能改名/下架，订单要能还原当时买的是什么、多少钱。

**索引**：`(coupleId, status)`、`(coupleId, createdAt)`。

## 五、接口（计划）

| action | 入参 | 返回 | 说明 |
|---|---|---|---|
| `shop.summary` | — | `{ balance, pendingCount, sub }` | 首页摘要 |
| `shop.detail` | — | `{ gifts, orders, config }` | 商城 + 我的券 |
| `shop.act` | `{ giftId, mode }` | `{ order }` | 下单（single/split） |
| `shop.pay` | `{ orderId }` | `{ order }` | 支付我这一份（扣爱心） |
| `shop.cancel` | `{ orderId }` | `{ order }` | 取消（已付的退款） |
| `shop.fulfill` | `{ orderId }` | `{ order }` | 对方确认已兑现 |
| `shop.giftAdd` | `{ name, emoji, price, fulfillment }` | `{ gift }` | 上架 |
| `shop.giftRemove` | `{ id }` | `{ ok }` | 下架（软删除） |

> `act` 只创建订单，不扣款；`pay` 才扣。这样合资时两边可以各点各的。

## 六、状态机

```
pending ──双方/单方付完──► paid ──对方确认兑现──► fulfilled
   │
   ├── 我取消 / 超过 24h 有人没付 ──► cancelled（已付原路退回）
   └── 单人购买：创建即 pending，pay 后直接 paid
```

| 状态 | 含义 | 能做什么 |
|---|---|---|
| `pending` | 等付款（合资时可能一方已付） | 付款、取消 |
| `paid` | 钱够了，等兑现 | 兑现、取消？（建议不可取消） |
| `fulfilled` | 已兑现 | 只读 |
| `cancelled` | 已取消/过期 | 只读；已付款已退 |

**过期用「读时惰性判定」**：读订单列表时，发现 `pending` 且 `createdAt + 24h < now` → 顺手取消并退款。
云开发没有常驻定时器，这是最省事且不容易错的做法。

## 八、实施步骤（依赖顺序）

### 第 0 步 · 先补账本原语（T59）

没有 `spend/refund`，商城不能开工。补的时候必须：
- 扣款前校验余额（T35）；
- 写流水 + 改余额尽量原子（T36）；
- 测试：余额不足被拒、重复扣款只扣一次。

### 第 1 步 · 服务端骨架

```
cloudfunctions/api/modules/shop/
├─ index.js     契约 + actions + onDecision（如果复用审批）
├─ store.js     只碰 m_shop_gifts / m_shop_orders
└─ rules.js     价格、状态机、过期、退款
```

### 第 2 步 · 契约

```js
module.exports = {
  key: 'shop',
  name: '礼物商城',
  emoji: '🎁',
  version: 1,
  collections: ['m_shop_gifts', 'm_shop_orders'],
  defaults: {
    maxPrice: 999,
    minPrice: 1,
    expireHours: 24,
    allowSplit: true
  },
  actions: { summary, detail, act, pay, cancel, fulfill, giftAdd, giftRemove },
  on: {},
  onDecision: {}
}
```

### 第 3 步 · 注册 + 建集合 + 前端

照 checkin 结构；`core/modules.js` 的 `shop` 条目 `enabled: true`。

### 第 4 步 · 测试

- 余额不足 → `INSUFFICIENT`；
- 独自购买：扣自己，生成券；
- 合资：A 付 5、B 未付 → pending；B 付 5 → paid；
- 24h 未付 → 读时取消 + 退款；
- 重复 `pay` → 只扣一次（`order:<id>:<openid>`）；
- 取消 → 反向流水，余额恢复；
- 兑现 → fulfilled；
- 流水总和 == 余额（每次操作后）。

### 第 5 步 · 验收

- [ ] 新增目录 + 注册表 2 行，0 处改打卡；
- [ ] 账本不变式全绿；
- [ ] 真机：上架 → 买 → 付 → 兑现 → 取消退款。

## 九、风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 扣款非原子 | 透支/多扣 | 先补 T35/T36；上商城前必须有事务或唯一索引 |
| 合资一方不付 | 订单挂 24h | 惰性过期 + 退款 |
| 礼物改名/删除 | 订单显示错 | 订单存快照 |
| 券不兑现 | 爱心花了没服务 | 对方确认 + 提醒（以后 notify） |
| 刷分 | 通胀 | 爱心只能靠打卡；不做转账 |
| 审核 | 虚拟货币/支付风险 | 明确「不可购买、不可充值」 |
