# 打卡规则文档

> 模块：`checkin` ｜ 版本：规则 v2（2026-10-26 定稿，S1–S4 已实现）
> 本文是**产品视角**：规则是什么、边界在哪、哪些能改。
> 技术实现见 [`开发文档.md`](开发文档.md)；早期规则设计已从工作区删除，原文在 git 历史里，当前规则以本文为准。

## 一、规则总览

| 项 | 默认值 |
|---|---|
| 打卡日切分 | 中午 12:00（12 点前算前一天） |
| 早睡窗口 | 21:30 – 24:00 |
| 早睡奖励 | 21:30–22:15 `+2`；22:15–23:15 `+1`；23:15–24:00 `0` |
| 早起窗口 | 06:00 – 12:00 |
| 早起奖励 | 06:00–09:00 `+1`；09:00–12:00 `0` |
| 漏打 | 每项 `-1`（扣到 0 封顶） |
| 申诉 | 早睡次日 12:00 前；早起次日 24:00 前（即关窗后 12 小时） |
| 月度全勤 | 一个自然月两项都打卡 ≥22 天 → `+10`（打满第 22 天当场发） |
| 同步奖 | 默认 `0`（关闭）；开后两人同一晚完成同一项各 `+1`（当前实现不对称，见下） |
| 爱心下限 | 0，不允许负数 |

## 二、打卡日（最重要的规则）

> **中午 12:00 之前的打卡，算前一天的。**

例子（默认 `cutoverHour = 12`）：

| 真实时间 | 打卡日 | 说明 |
|---|---|---|
| 10-26 22:30 早睡 | 10-26 | 当晚 |
| 10-27 06:40 早起 | 10-26 | **和上面是同一晚** |
| 10-27 11:59 早起 | 10-26 | 仍算前一晚 |
| 10-27 12:00 早起 | 10-27 | 从中午起算新一天 |
| 11-01 06:00 早起 | 10-31 | 算进 10 月日历 |

**为什么**：早睡在 D 日晚上、早起在 D+1 日早上。如果按自然日，两项永远不在同一天，「全勤/连续天数/月度 22 天」永远不成立。

**切分点的约束**：必须落在「没有打卡活动」的空档里，即
`早起结束时间 ≤ cutoverHour ≤ 早睡开始时间`。
默认 12:00 正好在 12:00（早起结束）和 21:30（早睡开始）之间。
填错会让日期整体偏移，校验器会拦。

## 三、早睡

窗口 `21:30 – 24:00`（左闭右开；`24:00` 表示当天结束）。

| 打卡时刻 | 爱心 | 说明 |
|---|---|---|
| 21:29 | — | 未开放 |
| 21:30 – 22:14 | **+2** | 第一档 |
| 22:15 – 23:14 | **+1** | 第二档（22:15:00 起算第二档） |
| 23:15 – 23:59 | **0** | 第三档：打了不算白打，日历照记 |
| 次日 00:00 仍未打 | **−1** | 关窗后结算；开放「晚睡说明」申诉 |

---

## 四、早起

窗口 `06:00 – 12:00`。

| 打卡时刻 | 爱心 | 说明 |
|---|---|---|
| 05:59 | — | 未开放 |
| 06:00 – 08:59 | **+1** | 第一档 |
| 09:00 – 11:59 | **0** | 第二档 |
| 12:00 仍未打 | **−1** | 关窗后结算；开放「晚起说明」申诉 |

> 早起窗口的「关窗」发生在**打卡日 D+1 的 12:00**，因为早起是第二天上午。
> 所以 D 日的早起，要到 D+1 中午 12:00 之后才确定缺卡。

## 五、月度全勤

| 项 | 规则 |
|---|---|
| 统计范围 | 一个自然月（按打卡日归属） |
| 「全勤一天」的定义 | 这一天早睡和早起**都打了卡**（有没有爱心都算） |
| 达标门槛 | ≥ 22 天 |
| 奖励 | `+10` 爱心 |
| 发放时机 | **打满第 22 天的那一刻**（不用等到月底） |
| 次数 | 每月一次（`idemKey = monthly:<YYYY-MM>`） |
| 统计口径 | 默认 `perUser`（各算各的） |

例子：

```
10-01 ~ 10-22 每天两项都打 → 10-22 当晚第二次打卡时，fullCount = 22
→ 立刻 +10，并记一条「月度全勤 2026-10 +10」
→ 之后 10-23 再打，不会重复发（同月 idemKey 已存在）
```

**注意**：
- 0 分档也算「打卡」，算全勤；
- 补签卡（以后）如果补的是 `checkins` 记录，也算全勤；
- 跨月的早起归到上个月，可能让上个月多一天、这个月少一天；
- `monthly.scope = couple` 目前**只存配置不生效**（代码只按 perUser 统计）。

## 六、漏打与申诉

### 6.1 漏打扣分

| 项 | 规则 |
|---|---|
| 扣多少 | 每项 `missPenalty`（默认 1） |
| 什么时候扣 | 窗口关闭后：早睡 D+1 00:00；早起 D+1 12:00 |
| 谁触发 | 定时器（每小时 :05）+ 打开小程序时的惰性结算 |
| 扣到 0 怎么办 | 停止扣，不产生负债 |
| 刚配对会被倒扣吗 | 不会，只结算 `pairedAt` 之后的打卡日 |
| 会扣几次 | 一次（`idemKey = miss:<type>:<day>`） |

### 6.2 申诉

| 项 | 早睡 | 早起 |
|---|---|---|
| 入口 | 打卡页漏卡卡片「说明一下」 | 同上 |
| 截止 | 次日 12:00（D+1 12:00） | 次日 24:00（D+2 00:00，关窗后 12 小时） |
| 理由 | 至少 2 个字 | 同上 |
| 审批人 | 对方 | 对方 |
| 同意后 | 退回扣掉的爱心（新增一条正向流水，原扣分保留） | 同上 |
| 拒绝后 | 扣分保留 | 同上 |

**流程**：

```
我提交 → 生成工单（late_night / late_wake）→ 对方「消息申请」看到
对方同意 → 退分（idemKey = appeal:<ticketId>）
对方拒绝 → 不变
```

**同一件事同时只能有一个待处理工单**（`refId = dayKey:type`），防连点。

> ⚠ **退款按配置扣分值，不按实际扣款额**：余额 0 时没扣，申诉通过仍会退一笔（T76）。
> 修复前不要把「申诉」当成赚爱心的途径；先记入待办。

**已知体验问题**：申诉通过后，漏卡卡片仍然在（因为那天确实没有打卡记录），且显示「已扣 N 爱心」。
卡片会保留到移出最近 4 天窗口。见 T34。

## 七、修改规则

```
我发起 → 生成「修改提案」（完整规则快照 + 变更摘要）
       → 工单 type = 'rules_change' 发给对方
对方同意 → 写入 core_settings，立即生效
         → 只影响之后的打卡；已发爱心不回滚
```

规则：

- **双方都同意才生效**：发起方提交即视为同意，对方点同意后才写入；
- **只影响之后**：爱心在打卡那一刻已写成流水，改规则不回头改账；
- **存完整快照**：同意后规则长什么样完全可预期；
- **有历史**：`core_settings.history[]` 保留最近 20 次，给「按当日规则结算」留口子；
- **校验**：本地 + 服务端都跑 `validateConfig`，非法配置提交不了。

## 八、可配置参数表

| 参数 | 默认 | 范围 | 界面可改 |
|---|---|---|---|
| `cutoverHour` | 12 | 0–23 整数，且落在空档 | ✅ 高级 |
| `sleep.window.start` | 21:30 | `HH:mm`，5 分钟倍数 | ✅ |
| `sleep.window.end` | 24:00 | 同上，支持 24:00 | ✅ |
| `sleep.tiers[].from/to` | 见上表 | 左闭右开，首尾相接，覆盖窗口 | ✅ 边界 |
| `sleep.tiers[].hearts` | 2/1/0 | 0–10 整数 | ✅ |
| `sleep.missPenalty` | 1 | 0–5 整数 | ✅ |
| `sleep.allowAppeal` | true | boolean | ❌ 只能改代码 |
| `sleep.appealDeadline` | 12:00 | `HH:mm` | ✅ |
| `wake.window.start/end` | 06:00 / 12:00 | 同上 | ✅ |
| `wake.tiers[]` | 1/0 | 同上 | ✅ |
| `wake.missPenalty` | 1 | 0–5 | ✅ |
| `wake.allowAppeal` | true | boolean | ❌ |
| `wake.appealDeadline` | 24:00 | `HH:mm` | ✅ |
| `monthly.requiredDays` | 22 | 1–31 整数 | ✅ |
| `monthly.bonus` | 10 | 0–100 整数 | ✅ |
| `monthly.scope` | perUser | `perUser` / `couple` | ❌ 只实现 perUser |
| `syncBonus` | 0 | 0–10 整数 | ❌ 只能改代码/配置 |

> 界面可改 ≠ 立即生效：改完要提交工单，对方同意才写入。

> ⚠ **同步奖未真正对称**：当前只在「后完成的人」打卡时给奖励，先完成的人不补发。
> 默认 `syncBonus=0` 所以不影响现在；开启前先修 T75。

### 8.1 不可配置（写死，保护一致性）

| 项 | 值 | 原因 |
|---|---|---|
| 爱心余额下限 | 0 | 不允许负余额 |
| 一天同一项只能打卡一次 | 是 | 否则可以刷 |
| 扣分只能用流水表达 | 是 | `余额 = 流水之和` 必须永远成立 |
| 规则修改必须对方同意 | 是 | 产品决定 |
| 打卡时间判定用服务器时间 | 是 | 防作弊 |

## 九、校验规则（`validateConfig`）

提交规则时会被拦的情况：

| 校验 | 错误示例 |
|---|---|
| `cutoverHour` 0–23 整数 | `-1`、`12.5` |
| 窗口时间 `HH:mm` | `9:00`、`24:00` 对 end 合法，对 start 不合法 |
| 窗口时间 5 分钟倍数 | `21:32` |
| 开始早于结束 | `23:00–21:00` |
| 至少 1 档 | `tiers: []` |
| 最多 8 档 | 9 档 |
| 第一档从窗口开始 | 窗口 21:30，第一档 21:40 |
| 最后一档到窗口结束 | 窗口 24:00，最后一档 23:00 |
| 档位首尾相接 | 第一档到 22:15，第二档从 22:20 |
| 每档开始早于结束 | `22:15–22:15` |
| 爱心 0–10 整数 | `-1`、`2.5`、`11` |
| 缺卡扣分 0–5 整数 | `6` |
| 申诉截止 `HH:mm` | `中午` |
| 全勤天数 1–31 | `0`、`32` |
| 全勤奖励 0–100 | `101` |
| `cutoverHour` 落在空档 | 填 23:00 或 06:00 |

`cutoverHour` 的校验条件：`wakeEnd <= cut <= sleepStart`。

## 十一、边界案例

| 场景 | 结果 |
|---|---|
| 22:14:59 打卡 | +2 |
| 22:15:00 打卡 | +1 |
| 23:14:59 打卡 | +1 |
| 23:15:00 打卡 | 0（记录，日历半透） |
| 23:59:59 打卡 | 0 |
| 00:00:00 打卡 | 未开放（等当天 21:30） |
| 次日 06:00 早起 | 打卡日 = 前一天，和昨晚早睡同一晚 |
| 次日 11:59 早起 | 打卡日 = 前一天 |
| 次日 12:00 早起 | 打卡日 = 当天；早起窗口已关 → 不能打 |
| 11-01 06:00 早起 | 打卡日 10-31，算 10 月 |
| 0 分档打了 | 算全勤，不发爱心 |
| 只打一项 | 不算全勤；连续天数中断 |
| 今天还没全勤 | 连续天数从昨天往回数，不打断 |
| 今天全勤了 | 从今天往回数 |
| 配对当天漏打 | 不扣（pairedAt 之前不结算） |
| 余额 0 漏打 | 不扣，不写流水（T33） |
| 申诉通过 | 退分；原扣分流水保留 |
| 同一天同一项申诉两次 | 第二次 `TICKET_EXISTS` |
| 改规则当天 | 只影响改完之后的新打卡 |
| 改规则后补算昨天 | 当前实现用新规则（T39） |

| 问题 | 建议 | 最晚决策 |
